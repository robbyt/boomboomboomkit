# Project Context for AI Agents

_This file contains critical rules and patterns that AI agents must follow when implementing code in this project. Focus on unobvious details that agents might otherwise miss._

---

## Technology Stack & Versions

- **Swift 6.0** — strict concurrency (`swift-tools-version: 6.0`), macOS 15+. All new public types MUST conform to `Sendable`
- **Zero external dependencies** — hard constraint, not observation. Only Apple system frameworks (Foundation, Accelerate, AVFoundation; plus CryptoKit + Synchronization, imported only by `ModelRegistry`). Do not introduce third-party packages
- **Accelerate/vDSP** — ALL bulk numeric operations must use vDSP. No manual `for` loops over signal buffers. Float precision for signals; **Double precision mandatory for IIR filters** (K-weighting biquads — Float causes measurable errors near unit circle poles)
- **AVFoundation** — audio file I/O only (PCMBufferReader). Imported via `@preconcurrency import AVFoundation` — do NOT remove this annotation (Apple types are not yet Sendable-annotated; this is the SE-0337 migration path). NEVER use `AVAsset.commonMetadata` for embedded BPM tags — it is async-only on macOS 13+ and Vorbis surfacing is historically inconsistent. Direct container parsing only (see `FileMetadataReader` for the pattern)
- **Swift Testing** — `@Suite`, `@Test`, `#expect`, `#require`. NOT XCTest
- **SwiftLint + swift format** — run `make fmt` BEFORE `make lint` (formatter can introduce lint violations). Formatter wins when rules irreconcilably conflict
- **SPM targets** — `BoomBoomBoomKit` (library), `BoomBoomBoomKitTestSupport` (shared fixtures + helpers for consuming packages — new test utilities go here, not in the test target), `BoomBoomBoomKitML` (CoreML/BNNS opt-in product — **no bundled `.mlmodelc`** since Story 4-6 Branch C; consumers BYOW via `BNNSTechnique(modelURL:) throws`; `Package.swift`'s `resources: [.copy("Resources")]` line is intentionally removed), `BoomBoomBoomKitTests` (unit tests, run by `make test`), `BoomBoomBoomKitBenchmarkTests` (env-gated corpus benchmarks: `OA300_CORPUS_PATH`, `GIANTSTEPS_CORPUS_PATH`, `PERF_BASELINE_DIR`, `ABLATION_PARALLELISM`, etc. — never run by `make test`). `tools/coreml-convert/` ships on main as the consumer convert tool (Story 4-4b DD #13 exception)

## Critical Implementation Rules

### Language-Specific Rules

- **Analyzers, results, and config are value types** — structs and enums, stateless `static` methods, no instantiation/lifecycle/dependency injection. Call directly (e.g., `BPMAnalyzer.estimateBPM(samples:sampleRate:options:)`). **Sole exception (Epic 9):** `ModelRegistry` is a `public final class` (`Sendable`, `Synchronization.Mutex`-guarded) — a standalone, in-memory consumer catalog of ML models with SHA-256 integrity validation, NOT part of any analysis pipeline. It is the only class in the core target; do not add others without a named story
- **Implicit nil** — never write `var x: T? = nil`. Swift optionals default to nil. The explicit `= nil` is redundant. Story 3-3a code review caught this for `mlTechnique`. Pattern: `public var mlTechnique: (any MLTechnique)?` not `... = nil`
- **ADR-11 Options-first public configuration** — All optional or defaulted configuration for public service methods MUST be passed via `AudioAnalysisService.Options`, NOT as method parameters on `analyzeBPM`. Two field-style conventions:
  - **Non-optional `T = .default`** — always-present (`intensity`, `mergeStrategy`, `maxSeconds`, `enableTrace`, `durationHint`, `votingPolicy`, `votingThreshold`, `metadataPolicy`, plus the Epic-8 beat-grid fields `beatGridCoverage`, `detectDownbeats`, `downbeatStrategy`, `beatGridTempoLock`, `refineBeatGridTempo` — all defaulting to a byte-identical no-op; see the `beat-grid` skill)
  - **Optional `T?`** — opt-in / protocol slots / overrides where `nil` carries semantic weight (`onProgress`, `techniqueSet`, `mlTechnique`)
  - Internal pass-through to `BPMAnalyzer.Options` retains memberwise init; public `AudioAnalysisService.Options` uses empty `init() {}` with property-level defaults — customize via mutation: `var opts = Options(); opts.intensity = .fastest`. Reference: `_bmad-output/planning-artifacts/architecture.md` ADR-11
- **`nonisolated(unsafe)` discipline** — used intentionally in three contexts, all documented inline: (1) `PCMBufferReader.downsample` for the synchronous `AVAudioConverterInputBlock` callback (do NOT refactor to `withCheckedContinuation` — introduces real concurrency where none exists), (2) test closures capturing mutable state in synchronous-only contexts (`isCancelled`, `onProgress`), (3) `FileMetadataReader` byte-parser scratch buffers with bounded `withUnsafeBytes` lifetime
- **Error handling** — `BPMAnalyzer` and `LUFSAnalyzer` return nil for no-result, never throw. `AudioAnalysisService` throws `PCMBufferReaderError` or `CancellationError`. `FileMetadataReader` (Story 3-6) never throws — metadata absence is not an error; uses bounds-checked `FileHandle` reads with `defer { try? fh.close() }`. Do not add new error types without explicit design decision
- **vDSP_Length wrapping** — all count parameters to vDSP functions require `vDSP_Length` (UInt, not Int). Always wrap: `vDSP_Length(count)`. Forgetting this causes compiler errors or silent truncation
- **CaseIterable + architecture invariants** — `DSPTechnique`, `BPMSelectionPolicy`, `OctaveEquivalencePolicy`, and `SignalSource` conform for ablation/enumeration. `Hashable` on `AnalysisIntensity`, `DSPTechnique`, `TechniqueSet`, `BPMSelectionPolicy`, `OctaveEquivalencePolicy`, `SignalSource`, `SignalWeights`, `ComputeBudget` (used as dictionary keys/Set members). `EnsemblePolicy` is NOT `CaseIterable` (the `.weightedVoting(SignalWeights)` associated value makes synthesis impossible — it provides a hand-written `allPolicies` list + `stableKey` instead). Architecture invariants (count assertions) are unit-test-locked — canonical list in Critical Don't-Miss Rules → API contract violations. Future refactors that flip them by accident fail at unit-test time, not corpus benchmark time
- **Code organization** — every file uses `// MARK: - Section` headers consistently. Public API gets `///` doc comments with `- Parameters:` and `- Returns:`. Internal helpers get minimal or no doc comments

### Public API Discipline (pre-1.0)

**Pre-release stability posture:** This library is pre-1.0 with zero external consumers today. **No backwards compatibility is promised in pre-release.** Breaking changes — renames, type relocations, removed cases, signature changes — are explicitly allowed and expected as we discover better designs. The `MLTechnique` labeled-tuple → `MLEvaluation` struct fix landing in Story 4.3 is the kind of break we'll happily make. ABI / source-stability commitment kicks in at 1.0; until then, prefer fixing mistakes over preserving them.

The discipline below is NOT about avoiding breaking changes. It's about **adding public API thoughtfully so we accumulate fewer mistakes to break later.** Every casually-promoted internal type is one more thing to clean up before 1.0; every labeled tuple in a public protocol signature is one more compiler-invisible Sendable hole.

**Epic 4 planning session (2026-05-04) applied this framing in three concrete decisions** — useful as reference precedent for future planning sessions: (a) `MLEvaluation` ships with only `bpm: Double` + `confidence: Double` — fields like `modelIdentifier`, `alternateCandidates`, `featureSetVersion`, `featureSummary` added per-story when a downstream consumer surfaces; (b) `EnsemblePolicy` enum case list NOT pre-locked from the Epic 4 spec — Story 4.4 author proposes cases based on Story 4.5 BNNS ablation evidence; (c) `MLTechnique.evaluate` input simplified to `BPMDiagnosticTrace` only (DSP candidates already carried in trace via `BarCandidate`) — no separate `candidates: [(bpm, score)]` parameter. In all three cases the planning room rejected "design once correctly, lock the surface" arguments because there are no consumers to lock for.

**Rules:** Every internal→public promotion is declared in the story spec's AC, not discovered in diff. The `MLTechnique` protocol is frozen — field expansions on `MLEvaluation` / `EnsembleDecision` require a named story spec, not deferred-work entries (m18 `rawMLBpm`, DN6 consumer-tunable thresholds, EC#02 NaN-safety were all asked-for and all declined to deferred-work with named re-open triggers). When a story's headline deliverable doesn't work, prefer Branch-C-style deletion over deprecation cycle (reference: Story 4-6 bundle pull).

- **Internal→public promotion requires a named story spec** that lists the promotion in AC, documents the use case, and considers alternatives. Story 3-3b's `HarmonicRatioEvidence` promotion is the reference precedent — declared in the story title and AC #1, not discovered in diff. Deferred-work entries are NOT sufficient — they are append-only and not re-read at PR time. Promotions discovered during code review (not pre-declared in AC) must either be reverted or back-filled with a story spec before merge. **Pre-1.0 caveat:** wrong promotions can be reversed later via deprecation + removal — but the cost compounds, so default to declaring the promotion explicitly even when reversal is cheap.

- **Public protocol signatures use named `Sendable` types for all parameters and return values.** No tuples (labeled or unlabeled), no inline closures returning tuples. `Sendable` conformance must be declared at the type definition, not inferred at the use site. Labeled tuples are structural types — they cannot conform to `Sendable` (SE-0302), `Equatable`, `Hashable`, or `Codable`; cannot be extended; cannot be DocC-documented as symbols; and cannot evolve without source breaks. The compiler cannot warn when a `[(bpm: Double, score: Float)]` parameter silently bypasses `Sendable` checking — only review can. **Reference defect:** `MLTechnique.evaluate(candidates: [(bpm: Double, score: Float)], trace: BPMDiagnosticTrace) -> (bpm: Double, confidence: Double)?` — fix landing in Story 4.3 via the named `MLEvaluation` Sendable struct (`{bpm: Double, confidence: Double}`) and a protocol that takes only `BPMDiagnosticTrace` as input (DSP candidates are already in the trace via `BarCandidate`). The original deferred-work entry suggested an additional `MLCandidate` struct; Epic 4 planning session 2026-05-04 dropped it under no-BC framing — add when a downstream story needs it (deferred-work.md, Story 3-3a code review; Story 4.3 spec).

- **Diagnostic and evidence payloads in public types use named `Sendable` value types** — never `[String: Any]` or `[String: <stringified-numeric>]` dictionaries. This aligns with Apple's Foundation migration from untyped `userInfo: [String: Any]` toward typed key namespaces (`URLResourceKey`, `FileAttributeKey`; WWDC 2021 "What's new in Foundation"). See `.claude/skills/bpm-diagnostic-trace/SKILL.md` for the typed-evidence pattern, four banned anti-patterns, and five audit grep recipes (A-E) — all five must return zero matches against `Sources/` and `Tests/` after any trace-field change. Story 3-3b migrated 4 trace fields and added 5 typed-evidence structs (`ClickCorrelationEntry`, `HarmonicRatioEvidence`, `SubBandVoteEvidence`, `DurationHintEvidence`, `BarCandidate`).

- **`CustomStringConvertible` is required for diagnostic/evidence types**, not for all public structs. Conform when the type surfaces in benchmark logs, ablation reports, or developer-facing trace dumps (the 5 typed-evidence structs qualify). Configuration types (`MetadataPolicy`, `VotingPolicy`, `Options`) and pure data carriers should NOT conform — synthesized `Mirror`-based descriptions are stable enough and `description` adds maintenance burden when fields change. Use `CustomDebugStringConvertible` if the format is debug-oriented rather than human-meaningful.

- **Access control boundaries** (post-Epic-9) — Public: `AudioAnalysisService`, `AnalysisIntensity`, `BPMSelectionPolicy` (8 cases; the renamed `CandidateMergeStrategy`), `DSPTechnique` (8 cases), `TechniqueSet`, `VotingPolicy`, `MLTechnique` (protocol frozen per Story 4-5 DD #18 — signature `evaluate(trace: BPMDiagnosticTrace) -> MLEvaluation?`), `MLEvaluation`, `EnsembleDecision`, `EnsemblePolicy` (Epic-6 reshape: 5 cases `.default`/`.dspOnly`/`.mlOnly`/`.highestConfidence`/`.weightedVoting(SignalWeights)`; NOT `String`/`CaseIterable`), `MLDiagnosticSnapshot`, `MLDiagnosticTechnique` (opt-in capability protocol; `BNNSTechnique` conforms, consumer `MLTechnique` impls may opt in), `BNNSTechnique`, `MLTechniqueError`, `PCMBufferReader`, `BPMDiagnosticTrace`, `ProgressUpdate`, `MetadataPolicy`, `MetadataSource`, `MetadataBPMEvidence`, `HarmonicRatio`, the 5 pre-Epic-6 typed-evidence structs (`ClickCorrelationEntry`, `HarmonicRatioEvidence`, `SubBandVoteEvidence`, `DurationHintEvidence`, `BarCandidate`), the Epic-6 unified-signal-pool surface in `SignalPool/` (`SignalWeights`, `SignalSource`, `OctaveEquivalencePolicy`, `EnsembleWeightResolution`, `SignalParticipation`, `WeightedSignal`, `AbstainReason`, `DemotionReason`, `SignalParticipationTraceEntry`), and the `FeatureSubstrate/` namespace (`OnsetFeatures`, `OnsetFeaturesBuilder`, `DecodedAudio`, `WeightingProfile`, `SubBandWeights`, `SubBandCutoff`, `AudioCodec`, `PrimingInfo`, `FeatureSubstrateError`; `MLFeatureFrames` + `TensorLayout` relocated here from `BPMDiagnosticTrace.swift`). `MLExecutionPolicy` and `ComputeBudget` are public but declared-and-not-yet-`Options`-wired (forward surface, Story 6.5a). Internal: `BPMAnalyzer`, `BPMResult`, `LUFSAnalyzer`, `LUFSResult`, `MelFilterbank`, `FileMetadataReader`, `UnifiedSignalPool`, `MetadataCorroborator` (relocated to `SignalPool/`; `EnsembleCombiner` removed in Story 6.4b — inlined into `AudioAnalysisService.combineEnsemble`). Public types used as AudioAnalysisService callback parameters (e.g., `ProgressUpdate`) are top-level, not nested. `Sources/BoomBoomBoomKitML/CoreMLTechnique.swift` placeholder remains untouched on disk; Story 4-8 was dropped under Branch C — re-open conditional on a future Branch-A retrain. **Epic 8/9 additions:** the beat-grid/downbeat public surface (`BeatGrid`, `BeatGridAnchor`, `BeatGridAnchorSource`, `BeatGridAnchorRepositionMode`, `BeatGridTempoLock`, `BeatGridCoverage`, `BeatTimestamp`, `DownbeatResult`, `DownbeatEstimate`, `MeterEstimate`, `MeterSource`, `DownbeatStrategy`, `TempoAgreement`, `CombinedAnalysisResult`) is public — its conventions live in the `beat-grid` project-local skill, not here. `LUFSReport` (public `struct`, `Sendable`/`Equatable`/`CustomStringConvertible`) is the public loudness output; `LUFSResult` stays internal. `ModelRegistry` (public `final class`, `Sendable`) + `ModelRegistryEntry` / `ModelRegistryError` / `ModelDigest` are a standalone SHA-256-validated consumer model catalog (the sole reference type in core), NOT wired into any analysis pipeline.

- **Product identity may diverge from library namespace pre-1.0.** The library namespace is `BoomBoomBoomKit`; the App Store consumer product is `BoomBoomBoom` (`com.robbyt.BoomBoomBoom`); the demo paths/scheme/xcodeproj/test-target stay `BoomBoomBoomKitDemo*` under Story 5-8 scope (b). ### Framework-Specific Rules (Accelerate/vDSP)

- **No manual loops over signal data** — every bulk numeric operation on audio buffers must use vDSP (`vDSP_vmul`, `vDSP_vadd`, `vDSP_vsdiv`, `vDSP_vthres`, `vDSP_vswsum`, `vDSP_rmsqv`, `vDSP_meanv`, `vDSP_dotpr`, `vDSP_vsq`, `vDSP_vramp`, etc.). Loops over *control flow* (iterating candidates, tracks, BPM values, click-pattern impulse positions) wrapping vDSP calls inside are fine — the prohibition is on `for i in 0..<count` over sample arrays. Story 3-2 replaced two manual phase-ramp loops in `tempogramMagnitude` and `computeFourierTempogram` with `vDSP_vramp`
- **FFT** — 2048 samples (power of 2 for radix-2), ~46ms frames at 44.1kHz. Use `vDSP.FFT` with split-complex format (`DSPSplitComplex`). **DC/Nyquist packing**: bin 0 of split-complex output packs DC in the real part and Nyquist in the imaginary part. Extract both BEFORE calling `vDSP_zvmags`, which otherwise computes `sqrt(DC^2 + Nyquist^2)` — neither value
- **Stride** — always explicit in vDSP calls (stride=1 for contiguous). Never assume default
- **Mel filterbank** — row-major dense matrix applied via `vDSP_mmul`. Constructed by `MelFilterbank` (enum namespace, no cases). Hz-to-mel uses O'Shaughnessy (1987)
- **K-weighting (LUFSAnalyzer)** — two cascaded biquad sections (high-shelf + high-pass) via `vDSP.Biquad<Double>`. Input samples converted Float-to-Double via `vDSP_vspdp` (vectorized, not per-element cast). Pre-computed coefficients for 44.1/48/96kHz ONLY — unsupported rates return nil, do not interpolate
- **Invariant DSP pipeline** — 9 unconditional steps in sequence: (1) energy scan, (2) silence check, (3) mel-spectrogram onset (with optional sub-band normalization), (4) adaptive thresholding, (5) autocorrelation (with optional ACF sharpening), (6) Fourier tempogram, (7) periodicity fusion, (8) peak selection, (9) range normalization 60-200 BPM. Plus three post-disambiguation steps: (10) sub-band voting octave disambiguation, (10b) sub-band peak confirmation, (10c) fine-grid refinement (gated by `.fineGridRefinement`). Steps 3/4/5/10/10c are technique-gated via `TechniqueSet`. **This spine never reorders.** The optional **step 11** (beat-grid extraction, gated by `BPMAnalyzer.Options.computeBeatGrid`, default `false` → branch not entered → byte-identical) is a PARALLEL fan-out running after 10c that does NOT feed or reorder the tempo spine; **step 12** is confidence. Conventions live in the `beat-grid` skill.
- **Optional gated rescore stages** — two stages run conditionally between step 9 and step 10:
  - **Step 9b — click-track cross-correlation rescore** (Story 3-3): gated by `.clickTrackCorrelation` ∈ technique set. Rescores candidate scores via normalized cross-correlation against synthetic click pattern. Rescored candidates flow into BOTH `resolveOctaveAmbiguity` AND back out via `BPMResult.candidates` so multi-window `BPMSelectionPolicy.merge` operates on the same values disambiguation saw (Story 3-3 DD#11). `trace?.rawCandidates` preserves pre-rescore values
  - **Step 9.7 — duration-derived BPM hint** (Story 3-4): gated by `Options.durationHint` AND `fileDurationSeconds >= Options.durationHintMinFileSeconds` (default 180s). Boosts candidates matching common bar-count BPMs (32, 64, 96, 128, 192, 256 bars). Same downstream contract as 9b
  - Sort the rescored/boosted array descending by score with explicit tiebreaker on original index — **`Array.sort` is not contractually stable in Swift** (Story 3-3 DD#6)
- **Click rescore signal-domain contract** — Step 9b operates on the **onset envelope (~100 Hz)**, NOT on raw audio at 44.1 kHz. Synthetic click pattern is K=8 unit impulses spaced at `60 * onsetRate / bpm` frames, cross-correlated against the envelope. **No audio-domain mixing, no PCM clipping risk, no LUFS coupling, no DC bias.** The `.clickTrackCorrelation` name pattern-matches to audio-domain click tracks (Logic Pro, AVAudioEngine) — the implementation is a similarity computation in envelope space, not signal injection. See `BPMAnalyzer.clickRescore` and Story 3-3 DD#2 for the 441× cost rationale
- **Pipeline step numbers are stable identifiers** — once a step number ships in a trace key, benchmark artifact filename, or completion-note diagnostic, it does NOT move. The fractional/letter suffix convention (`9b`, `9.7`, `10b`, `10c`) encodes insertion semantics: letter suffix = sibling stage at same logical position; fractional = insertion between integer steps; reserved gaps (e.g. 9.6 left free by Story 3-4 for a future candidate-pruning pass) are intentional headroom for future stories. Renumbering 1→N cleanly is forbidden — it silently breaks diagnostic traceability across `_bmad-output/implementation-artifacts/` JSON, `BPMDiagnosticTrace` keys (post Story 3-3b namespacing), and historical story-ID-to-step mapping
- **AudioAnalysisService window loop** — PCM read once, then loop iterates `intensity.windowSizes` calling `BPMAnalyzer.estimateBPM()` per window. Cancellation/progress hook into loop iteration. Results merged via `BPMSelectionPolicy` post-loop. Never re-read PCM per window
- **Cancellation (AudioAnalysisService)** — injectable `isCancelled: @Sendable () -> Bool` (defaults to `{ Task.isCancelled }`). Checked before PCM read and before each window. Throws `CancellationError` — nil means "no BPM detected," CancellationError means "user cancelled" (`try?` callers get nil for both). Between-windows only (ADR-1), never mid-window
- **Progress (AudioAnalysisService)** — `onProgress: (@Sendable (ProgressUpdate) -> Void)?` fires BEFORE each window with `(windowsCompleted, windowsTotal)`. No completion callback — function return signals completion. Tracks windows attempted, not windows producing results
- **Buffer structs (BPMAnalyzer)** — `PipelineBuffers`, `ACFBuffers`, `TempogramBuffers`: `static func allocate(...)` factory + `func deallocate()` cleanup + `defer { buffers.deallocate() }`. Lifetime: single `estimateBPM()` call. Allocate unconditionally (not per-technique). Allocate at highest owning scope, pass to helpers as parameters

### Pool-Authoritative Selection Boundary (KDD-A6 Stage 3, Story 6.5b)

The authoritative production selection is `BPMSelectionPolicy.select(from: pool)` — a two-phase pool-consuming entry point. **Phase 1** runs the byte-preserved cross-window `merge`; **Phase 2a** runs the multiplicative metadata corroboration (the corroboration core, scaled by `SignalWeights.fileMetadata`). The cross-signal ML fusion (**Phase 2b** — `AudioAnalysisService.combineEnsemble` + the KDD-A5 weighted resolution) runs AFTER ML evaluation in the service, because `MLTechnique.evaluate` reads the post-corroboration trace (the no-accuracy-change ordering is load-bearing). The corroboration can promote a non-winning candidate to the chosen BPM.

- **`select` orchestrates `merge` (Phase 1) then corroboration (Phase 2a).** The `UnifiedSignalPool` is authoritative (built unconditionally, not nil on the default path) and carries the per-window DSP candidates + parsed metadata + pre-computed ML participation. Single-window paths (intensity 1-5) still receive corroboration — `merge` short-circuits on a one-window pool, then Phase 2a runs.
- **Corroboration can change the winner via multiplicative boost re-selection.** Boost is multiplicative `policy.corroborationBoost = 1.25×`, scaled by `metadataScale = SignalWeights.fileMetadata` as `1.0 + metadataScale·(1.25−1.0)`; clamped to `policy.maxBoostedConfidence = 0.95` (never reaches `1.0` by construction). Boost is applied to ALL candidates matching any participating tag, then the winner is re-selected. Penalty path (DSP-disagrees-with-unanimous-tags) is multiplicative `1.0 − metadataScale·(1.0 − 0.85)` with a divide-by-zero guard. At `metadataScale == 1.0` (every non-`weightedVoting`/`default` policy) the boost/penalty reproduce the pre-6.5b `1.25`/`0.85` exactly. **`Options.metadataPolicy = .disabled` produces output-equivalent (DD #10 semantic, not byte) `bpm`/`confidence`/per-candidate output to the pre-metadata pipeline** — the regression-protection contract, now guarded by `MergeSemanticEqualityTests` + the corpus accuracy floors (Story 6.5b retired the byte floor).
- **`merge` keeps its `BPMResult?` signature; it is Phase 1 of `select`.** `merge`'s signature is unchanged — the 41 test/benchmark call sites drive it directly as a standalone cross-window aggregator. New cross-signal corroboration runs inside `select`'s Phase 2 (the corroboration core / `combineEnsemble`), never as `merge` parameters. `MetadataCorroborator.apply` is the Phase-2a corroboration core (threaded `metadataScale`); it is no longer invoked standalone in production.
- **Metadata is NOT a `DSPTechnique` case.** It's a file-level signal orthogonal to DSP, gated by `Options.metadataPolicy.enabledSources: Set<MetadataSource>`. `DSPTechnique.allCases.count == 8` is a unit-test-locked invariant (Story 4-7 added `.superFluxOnset` as the eighth case); adding metadata as a DSP case would silently break the 256-combo ablation matrix

### Testing Rules

- **Swift Testing only** — `@Suite`, `@Test`, `#expect`, `#require`. Never XCTest. Use `#require` when a nil/failure would make subsequent assertions meaningless; use `#expect` for validating properties of a known-good value
- **Separate benchmark test target** — `BoomBoomBoomKitBenchmarkTests` is a distinct SPM target from `BoomBoomBoomKitTests`. Run via `swift test --filter BoomBoomBoomKitBenchmarkTests.<Suite>` or Makefile targets (`make benchmark`, `make benchmark-giantsteps`, `make oracle`, `make ablation`, `make ablation-smoke`, `make perf-benchmark`, `make click-impact-report`, `make duration-impact-report`, plus the Epic-7/8 targets `make benchmark-beatgrid`, `beat-grid-impact-report`, `tempo-refine-impact-report`, `combined-analyze-impact-report`, `shared-decode-impact-report`, `consistency-rate-oa300`, `accuracy-forensics` — the four wall-clock gates run under `swift test -c release`). `make test` runs ONLY `BoomBoomBoomKitTests` — corpus-gated benchmarks never activate in unit-test runs. Story 2-3 separation is the regression-protection backbone
- **JAMS ground-truth + beat-grid F-measure floor** — ground-truth corpora (OA300, DAW oracle, DnB targets) are JAMS 0.4 `{entries:[...]}` wrappers since Stories 8.8a-c, decoded through the public `JAMSDecoder` in `BoomBoomBoomKitTestSupport` (unknown JAMS namespaces are rejected, never silently defaulted). Beat-grid acceptance is a three-step `make benchmark-beatgrid`: Swift emits estimated beats + asserts coverage/drift/downbeat, a develop-only Python `mir_eval` sidecar computes the F-measure, then `BeatGridFloorTests` asserts the committed floor. The floors are regression nets below the epic target — full mechanism + the accept-as-shipped posture live in the `beat-grid` skill
- **Test fixtures** — accessed via `AudioFixtures.url(for:extension:)` from `BoomBoomBoomKitTestSupport`. Synthetic click tracks via `TestSignalGenerators.generateClickTrack(bpm:sampleRate:durationSeconds:)` (audio-rate, exponential decay over 64 samples, for full-pipeline tests). For envelope-rate direct testing, call `BPMAnalyzer.synthesizeClickPattern(bpm:onsetRate:clickCount:)` via `@testable import` (internal, ~100 Hz unit impulses). `createClickTrackWAV(bpm:sampleRate:durationSeconds:url:)` is duplicated across three test files — TestSupport promotion deferred
- **Suite initializers** — `init() throws` loads fixtures and ground truth. Each `@Test` gets a fresh suite instance, so init runs per-test (not per-suite). Fixture loading is fast (JSON parse); expensive work (audio analysis) happens within each test. See `OA300BenchmarkTests`, `DAWOracleBenchmarkTests` for the pattern
- **Env-gated benchmarks** — OA300 tests require `OA300_CORPUS_PATH`; GiantSteps requires `GIANTSTEPS_CORPUS_PATH`; perf baselines require `PERF_BASELINE_DIR`; ablation parallelism via `ABLATION_PARALLELISM`; impact reports via `CLICK_IMPACT=1` / `DURATION_IMPACT=1` / `CLICK_IMPACT_OUT_DIR` / `DURATION_IMPACT_OUT_DIR`. Pattern: `@Suite("Name", .enabled(if: ProcessInfo.processInfo.environment["OA300_CORPUS_PATH"] != nil))`
- **Two levels of parallelism, both bounded** — `make test` runs `swift test --parallel` (SPM-level suite parallelism). Within benchmarks, `withTaskGroup` parallelizes track analysis. Story benchmark-infra-ablation-parallelism replaced unbounded `withTaskGroup` in `AblationFullMatrixTests.fullAblationMatrix` and `smokeAblation` with `batchedTaskGroup(items:parallelism:body:)` — default `min(activeProcessorCount, 32)`, override via `ABLATION_PARALLELISM` env (range `[1, 128]`). Use `make test-verbose` (no `--parallel`) when debugging failures

### Code Quality & Style Rules

- **`make fmt` then `make lint`** — always in this order. swift format may introduce lint violations (verified: `closure_parameter_position` conflict). Run both before committing
- **SwiftLint disabled rules** — 11 rules disabled in `.swiftlint.yml`. Only disable rules that irreconcilably conflict with swift format or are impractical for DSP-heavy code (file_length, function_body_length, cyclomatic_complexity). Do not disable rules just because they are inconvenient
- **TODO comments** — `// TODO:` triggers SwiftLint warnings intentionally; do NOT suppress with `swiftlint:disable:next todo`. `Sources/` currently carries ZERO `// TODO:` comments, so `make lint` is expected clean on the Swift side — any new `// TODO:` is a net-new warning that must be justified in the story that adds it (the old grandfathered `LUFSAnalyzer.swift:94` baseline is gone)
- **File naming** — PascalCase matching the primary type (`BPMAnalyzer.swift`, `DSPTechnique.swift`, `MetadataPolicy.swift`, `FileMetadataReader.swift`). Test files: `<TypeName>Tests.swift`
- **Header format** — six-line standard: `//` / `//  FileName.swift` / `//  BoomBoomBoomKit` / `//` / `//  Brief description` / `//`
- **Imports** — explicit per file. `Foundation`, `Accelerate`, `AVFoundation` imported only where directly used. Do not add redundant imports or remove seemingly-unnecessary ones
- **Academic and standards references** — cite papers, standards, and specifications inside `///` doc comments on the relevant declaration (e.g., `/// ... (Davies & Plumbley 2007)`, `/// ITU-R BS.1770-5`, `/// ID3v2.4 §4.2.1`, `/// ISO/IEC 14496-12 §8.4.2`). For container/metadata parsing (`FileMetadataReader`), cite the spec section, not just the spec name. **When no Apple precedent exists for a DSP technique, cite the original signal-processing literature** (e.g., Lewis 1995 "Fast Normalized Cross-Correlation" for the sparse beat-search pattern in `clickRescore` DD#6) — do NOT claim WWDC precedent that doesn't exist
- **Never name GPL / third-party inspiration sources in source code or public-facing PRs** — we draw inspiration from (and improve substantially on) projects like aubio, but their names MUST NOT appear in `Sources/`, `Tests/`, commit messages, or PR titles/bodies. Source doc comments and public PRs cite only the underlying academic literature (Davies & Plumbley, Ellis, etc.) and state "clean-room implementation from the academic literature; no third-party source transcribed or linked." Referencing those projects is fine ONLY in develop-only Markdown (story specs, `project-context.md`, `deferred-work.md`) — those are private. This supersedes any story AC that says to cite the inspiration source by name in code (e.g., Story 8.4 AC2's "cite `aubio/.../beattracking.c` for inspiration"): keep the GPL fence (no transcription, no linkage, zero deps) but express it without naming the source

### Story Authoring Discipline

These are workflow patterns that emerged through Epic 1-3 retros and are now load-bearing for any non-trivial story. **This subsection is the canonical home for HALT, PSI, KDD, multi-pass review, diagnostic-state design, and `deferred-work.md` SoT rules.** Other subsections cross-reference here rather than restating.

- **Key Design Decisions (DD) block at the top of every story spec** — numbered list of 2-12 design decisions the Project Lead reviews BEFORE dev begins. Stories 3-3 (13 DDs) and 3-6 (12 DDs) are the reference precedents. The DD block is the surface that pre-implementation Codex review walks first
- **Previous Story Intelligence (PSI) section** — every story cites 3-5 learnings from the immediately-preceding story: commit SHA, accuracy floors held, test patterns reused, gating-checklist outcomes. Established as habit by Story 2-2; mandatory throughout Epic 3
- **Pre-implementation multi-pass Codex review is load-bearing** for any story with new public API or DSP behavior. Three layers: (1) **Failure Mode Analysis** — single-pass, walks every AC asking "what's the most plausible way this fails?"; (2) **Self-Consistency review** — 3 parallel Codex agents (Blind Hunter, Edge Case Hunter, Acceptance Auditor) each critique the post-FMA spec; (3) **Code review** on the staged diff. Story 3-5 caught two self-introduced contradictions from layer (1) only via layer (2). Story 3-3 caught a kernel-pre-reverse direction inversion before any code landed. Skipping any layer for non-trivial stories has historically cost more than running the layer
- **Architecture cascade review** — for stories touching shared signatures (e.g., `BPMSelectionPolicy.merge` has 41 call sites), the pre-implementation review MUST count call sites and propose architecture that preserves the signature. Story 3-6 v1.2 reversed its original return-tuple architecture after Codex flagged the cascade — final design extracted a named caseless-enum namespace (`MetadataCorroborator`) + post-`merge` apply step rather than expanding `merge`'s parameter list. Story 6.5b kept `merge`'s `BPMResult?` signature intact (the 41 sites unchanged) while introducing the pool-authoritative `BPMSelectionPolicy.select(from:)` that wraps `merge` as Phase 1 — the production selection flip happens around `merge`, not through its signature
- **`deferred-work.md` is the authoritative single source of truth for deferred items**, NOT story-file `[ ]` checkboxes. When a later story addresses an earlier story's review item, EITHER: (a) the dev agent's commit flips the prior story's checkbox to `[x]` with a one-line cross-reference to the addressing commit/story, OR (b) the item migrates to `deferred-work.md` with explicit category. Story files capture point-in-time review state and drift when later work addresses items without updating them. **Epic close-outs include a sweep that resolves every still-open `[ ]` in the epic's stories** — Epic 3 retro's Story 3-2 cleanup is the reference precedent
- **HALT discipline** — when implementation reveals an AC violation that can't be resolved within the story's authorized scope (e.g., Story 3-4 GiantSteps regression at spec-literal hint values), the dev agent MUST halt and surface the finding to the Project Lead with concrete options. Do NOT silently relax the AC or invent a new threshold. Story 3-4 Task 7 (180s minimum-file-seconds threshold) is the reference precedent for a user-authorized post-HALT spec amendment. Epic 4 fired 7+ HALT events; all were surfaced with concrete options, none silently relaxed
- **Diagnostic state must be designed BEFORE the technique that needs it.** When a new technique's failure modes are not directly observable via existing `BPMDiagnosticTrace` surface, the story spec MUST include a "Diagnostic state" section answering: *what must the trace carry for this technique's behavior at failure to be debuggable from a single corpus run?* Story 4-6's `MLDiagnosticSnapshot` + `MLDiagnosticTechnique` capability protocol is the reference precedent — it was added AFTER Story 4-5's 100%-abstain alarm to disambiguate among 5 possible failure modes. The cost of designing it pre-need is materially lower than the cost of debugging without it
- **Story author / dev agent MUST Read the existing target code before authoring a story that claims to change it.** Skipping this risks shipping a no-op duplicate or a spec written against a false premise (reference: Story 4-7 mid-flight rescope when `computeMelOnsetEnvelopeWithSubBands` was misread as energy-based when it was log-mel spectral flux)
- **`deferred-work.md` is the canonical single source of truth for deferred items** (Epic 4 retro A2). Story specs may list review findings, but the canonical resolution ledger is `deferred-work.md` only. Close-out commits MUST add a cross-reference entry in `deferred-work.md` for every applied patch and every deferred item. Story-file `[ ]` checkboxes are advisory, not authoritative — they drift when later stories address findings without checking them off
- **5-layer review cadence for any story with new public API, DSP behavior, or consumer-facing UI.** Pre-PR: (1) Failure Mode Analysis single-pass + (2) Self-Consistency review with 3 parallel Codex agents (Blind Hunter + Edge Case Hunter + Acceptance Auditor) + (3) Code review on staged diff. Post-PR: (4) Codex MCP `codex:consult` for cross-validation when warranted + (5) GitHub Copilot inline review comments triaged into patches/defers/dismissals as a Review Findings appendix. Epic 5 confirmed the cadence catches real defects (privacy-manifest `35F9.1` reason, ISO 8601 millisecond truncation, validateDropPayload URL guard, INFOPLIST_KEY_CFBundleName ASC default-name leak) that no single layer would surface. Story 5-7 ran four nested review sub-sections under this cadence and remains the high-water mark
- **Story-spec compaction discipline at close-out.** When a story acquires a 3rd review sub-section OR a mid-flight pivot rewrites a KDD, schedule a 50% compaction pass at close-out — shipping-state-only spec body, full revision history compacted to a single Change Log section. Default ceiling: no story spec exceeds 350 lines at `done` status without an explicit "audit-trail-preservation override" Change Log entry. Story 5-7 (552 lines, 4 review sub-sections) and Story 5-8 (363 lines with retained scope-c mechanics) are the precedent that motivated the rule
- **Supersession-header amendment pattern for cross-story KDD overrides.** When a later story supersedes an earlier story's KDD, add a `> AMENDED BY X-Y — KDD partially superseded.` blockquote at the head of each affected KDD with cross-reference to the superseding story. Original wording preserved beneath for archaeological reasons. Precedent: Story 5-8 KDD #4 amending Story 5-7 KDD #4 + #5. Do NOT delete superseded text; the audit trail of what was true when is load-bearing for pre-1.0 reasoning
- **Pre-execution-decisions-before-irreversible-edits ceremony for one-way doors.** When a story's mechanics are reversible (LOC edit in a Swift file, test addition, doc rewrite) the standard DD block suffices. When the mechanics are irreversible (bundle ID committed to ASC, license changes, database schema migrations past a public release, public API removals post-1.0), the story spec MUST capture pre-execution trade-off decisions in Completion Notes BEFORE any mechanic lands — including the alternative paths considered and rejected. Story 5-8 captured 5 such trade-offs (trigger, persona, scope, name, story shape) before any pbxproj edit; the discipline caught the "Apple welds bundle IDs on first upload" constraint in time to choose the final name. Apply selectively — not every story is a one-way door
- **After flipping a policy during spec review (e.g., self-heal vs. preserve, throw vs. fallback), grep all Verification / Manual-checks / I/O-matrix sections for stale expectations of the old policy.** The Codex spec-review pass for the merge-strategy-persistence story flipped the unrecognized-rawValue policy from "preserve on disk" to "self-heal: remove and fall back" — but a leftover Verification line still asserted the old "preserved on disk" expectation. Codex's review caught the flip but not the dangling Verification; GitHub Copilot caught it post-push (PR #16 comment 3). Cost: one follow-up commit. Run the grep BEFORE pushing, as part of the same compaction pass that the previous rule mandates

### Critical Don't-Miss Rules

**Silent correctness failures:**
- **Never use Float for IIR filter coefficients** — K-weighting biquads require Double. Float32 causes measurable LUFS errors near unit circle poles. Code compiles fine; results are silently wrong
- **Accuracy regressions** — any change to `BPMAnalyzer` must be validated against OA300 + GiantSteps corpora (`make benchmark`, `make benchmark-giantsteps`). CI floors (the `#expect` gates): OA300 Acc1 ≥ 57/82 + Acc2 ≥ 73/82; GiantSteps Acc1 ≥ 537/661 + Acc2 ≥ 546/661 (current measurement runs ahead of the OA300 gate at 58/82 + 74/82). **All four floors are unconditional `#expect` assertions in `OA300BenchmarkTests` and `GiantStepsBenchmarkTests`** — they fire on every CI run regardless of preset/policy membership. Run `make oracle` for three-way DAW comparison on ambiguous cases. Run paired byte-equality opt-out test for any new `Options`-gated feature
- **In-place signal mutation** — pipeline steps should mutate `[Float]` arrays in-place where possible (vDSP supports overlapping input/output). Do not copy signal buffers between steps — 120s of audio at 44.1kHz is ~10MB per copy
- **DSP single-window Acc1 ceiling on OA300 is 55/82 (67.1%)** — documented in 256-combo ablation (was 128 pre-Story-4-7; the new `.superFluxOnset` case did not break the ceiling). Default `Options` reaches 58/82 via multi-window aggregation + merge + metadata corroboration. **Pure technique-tuning in the existing 8-case `DSPTechnique` family is at saturation.** Future "DSP accuracy improvement" stories at default intensity must either (a) change architecture (top-K refinement, post-disambiguation merge), (b) target a different intensity, or (c) operate on a different signal axis (file metadata, ML features). "Add another `DSPTechnique` case to fix accuracy" is no longer viable without architecture change
- **ML is BYOW; default `Options` has no ML.** `Options.mlTechnique == nil` by default. No `.mlmodelc` ships on main. Consumers wanting ML augmentation construct `BNNSTechnique(modelURL:) throws` against their own compiled model. **Quality bar:** the previously-bundled `giantsteps_v1.mlmodelc` was pulled in Story 4-6 Branch C — Outcome D, model genuinely too weak (forensics at `_bmad-output/implementation-artifacts/4-6-ml-accuracy-investigation-and-bundle-decision.md`: `wrong_non_abstain_count=54/82` at forced-accept, `softmax_max_p95=0.294`, bimodal predictions at 125/175 BPM regardless of input). Consumer models should clear (a) the 4 named DnB triplet targets in `Tests/BoomBoomBoomKitBenchmarkTests/Fixtures/4-dnb-triplet-targets.json` AND (b) the OA300 ablation 55/82 single-window Acc1 ceiling before being framed as a "default-ready" model. A first Branch-A retrain WAS attempted — Epic 7's `giantsteps_v2` was evaluated against the formal FR-18 5-gate promotion evaluation (DnB sentinels; OA300 Acc1 strictly > 55/82; GiantSteps Acc1 ≥ 537/661; ECE-half/double < 0.10; tail-error P95; aggregated ≥2-of-3 seeds, bound to `MLDiagnosticSnapshot.decodedBPM` not the DSP-contaminated `result.bpm`) and FAILED → closed BYOW (2026-06-09, `make epic7-freeze DECISION=byow`). The FR-18 gates (`_bmad-output/implementation-artifacts/7-6-fr18-promotion-gate-and-fr23-octave-consistency-report.md`) are now the bundle-vs-BYOW quality bar; the v1 forensics are historical precedent. Library default accuracy IS the DSP accuracy

**Memory safety:**
- **UnsafeMutablePointer discipline** — every `.allocate(capacity:)` MUST have a corresponding `.deallocate()` in a defer block or explicit cleanup. See `PipelineBuffers`, `ACFBuffers`, `TempogramBuffers` for the pattern (struct with `allocate()` factory and `deallocate()` method)
- **Buffer zeroing** — `[Float]`: `vDSP.clear(&array)`. `UnsafeMutablePointer<Float>`: `vDSP_vclr(pointer, 1, vDSP_Length(count))`. Never `pointer.initialize(repeating:count:)` on reused buffers (UB on second use)
- **`FileHandle` discipline** — `FileMetadataReader` byte parsers use `defer { try? fh.close() }` to guard against fd leaks under the 300-track benchmark (Story 3-6). Never leave a `FileHandle(forReadingFrom:)` unguarded
- **OGG is NOT supported** — `AVAudioFile` supports WAV, AIFF, CAF, MP3, AAC/M4A, FLAC. OGG/Vorbis has no native Core Audio codec on macOS

**API contract violations:**
- **Never add `throws` to analyzers** — `BPMAnalyzer` and `LUFSAnalyzer` return nil for no-result, never throw. `AudioAnalysisService` throws `PCMBufferReaderError` and `CancellationError` only. `FileMetadataReader` (Story 3-6) never throws — metadata absence is not an error. Do not add new error types without explicit design decision
- **Internal-to-public promotions require explicit story spec** — `BPMAnalyzer`, `BPMResult`, `LUFSAnalyzer`, `LUFSResult`, `MelFilterbank`, `FileMetadataReader`, `MetadataCorroborator` are internal by design. The public facade is `AudioAnalysisService` (plus the configuration/evidence types listed in Language Rules → Access control boundaries). **Promotions are allowed but require a named story spec** documenting the use case (Story 3-3b's `HarmonicRatioEvidence` promotion is the reference precedent — declared in story title and AC #1, not discovered in diff). See "Public API Discipline (pre-1.0)" in Language Rules
- **Architecture invariants are unit-test-locked (canonical list)** — `DSPTechnique.allCases.count == 8` (Story 4-7), `TechniqueSet.allDSPCombinations().count == 256` (2^8), `MetadataSource.allCases.count == 3`, `BPMSelectionPolicy.allCases.count == 8` (the renamed `CandidateMergeStrategy`), `OctaveEquivalencePolicy.allCases.count == 3` (Story 6.5a, locked in `EnsembleConfigTypesTests`), `TechniqueSet.optimal.contains(.clickTrackCorrelation) == false`. Semantics may want revisit in Epic 5 (deferred-work W1 + Epic 4 retro T5).
- **`BPMSelectionPolicy.merge` keeps its `BPMResult?` shape; it is Phase 1 of `select`** — 41 test/benchmark call sites drive `merge` directly as the standalone cross-window aggregator. The authoritative production selection is `BPMSelectionPolicy.select(from: pool)` (Phase 1 `merge` + Phase 2a multiplicative corroboration scaled by `SignalWeights.fileMetadata` + service-side Phase 2b ML fusion / KDD-A5). New cross-signal corroboration runs inside `select`'s Phase 2, never as `merge` parameters. See "Pool-Authoritative Selection Boundary" subsection
- **Never use `AVAsset.commonMetadata` for embedded BPM tags** — async-only on macOS 13+, Vorbis surfacing through AVFoundation is historically inconsistent on macOS. Use direct container parsing (`FileMetadataReader`'s MP4 atom walker / ID3v2.3-2.4 frame walker / FLAC Vorbis comment parser). Reference: Story 3-6 v1.2 + Apple Docs MCP validation

**Banned trace-field shapes:**
- **Four anti-patterns explicitly forbidden** in `BPMDiagnosticTrace` and any future evidence types: (1) `[String: Float]?` keyed by `%.1f` BPM (collision risk — two candidates rounding to same one-decimal label collapse silently), (2) `[String: String]?` with stringified-numeric values (precision loss + parse cost), (3) CSV-serialized arrays inside dict values (heavy parse cost), (4) stringly-typed enums-as-string-values (type-erasure). All four checked via `.claude/skills/bpm-diagnostic-trace/SKILL.md` audit recipes A-E before any trace change merges. Story 3-3b is the canonical migration — `Sources/` and `Tests/` are provably clean post-migration

**ML provenance discipline:**

_For the discipline rule on designing trace state BEFORE introducing techniques that need it, see Story Authoring Discipline → "Diagnostic state must be designed BEFORE the technique that needs it."_

- **`MLTechnique` protocol is frozen** (Story 4-5 DD #18) — `evaluate(trace: BPMDiagnosticTrace) -> MLEvaluation?`. Field expansions on `MLEvaluation` / `EnsembleDecision` require a named story spec, not deferred-work entries
- **Never add `name` to `MLTechnique`** — Story 4-3 HALT-(b) zero `mlTechnique.name` matches is a unit-test invariant. The protocol surface stays minimal
- **`MLDiagnosticTechnique` is a capability protocol** — conformance is opt-in; consumers' `MLTechnique` impls are not required to conform. `BNNSTechnique` conforms; future `CoreMLTechnique` would too if Story 4-8 re-opens
- **`enableTrace` and `enableMLDiagnostics` are separate gates** (Story 4-6 review pass P17) — `Options.enableTrace` populates `BPMDiagnosticTrace` for DSP diagnostics; `Options.enableMLDiagnostics` populates `MLDiagnosticSnapshot` via `MLDiagnosticTechnique`-conforming techniques. Never re-merge them; the split exists because ML diagnostic state has different lifecycle and cost than DSP trace state, and the two consumer audiences (DSP debugging vs. ML calibration) are distinct
- **The FR-21 feature-drift version is centralized** in `MLFeatureFrames.currentFeatureSetVersion` — now `"v2"` (bumped from `"v1"` in Story 7.5). `BPMAnalyzer` stamps it and `BNNSTechnique.supportedFeatureSetVersion` references it; never hardcode the string. Any mel/FFT/log-shape change bumps this ONE constant (train/runtime drift tripwire)
- **`BNNSTechnique.modelInputTensor(from:)` is an `@_spi(FeatureParity) public static` featurize parity seam** (Story 7.5) — the single transpose→z-score→resample-to-W=512 implementation the instance `featurize` delegates to, reached by the develop-only `dump-model-input` CLI via `@_spi(FeatureParity) import` to byte-verify the Python trainer. It is NOT stable public API; promoting it out of `@_spi` requires a named story

**Release process:**
- **Never commit AI tooling to main** — `.claude/`, `_bmad/`, `CLAUDE.md`, `scripts/`, `_bmad-output/` stay on `develop` only (`Makefile` ships). Public `main` must not reflect LLM-aided development

**Future optimization notes:**
- `ContiguousArray` is NOT needed for `[Float]` — Swift's `Array` is already contiguous for value types (no ObjC bridging check). The ~15% `ContiguousArray` improvement only applies to arrays of class types. Current `[Float]` usage is optimal
- `reserveCapacity` on intermediate arrays when size is known ahead of vDSP operations
- **Onset-envelope quality on heavily-mastered material is the upstream weakness** — clipped/limited DnB has flatter onset peaks, which weakens onset detection (step 3) before any later step can rescore. The 4 named DnB triplet failures (Charly, Faraday_Bunker, Yin Yang, HEFT_Anagram 6) likely have this as a contributing cause. Epic 4 ML feature engineering should ingest features that are robust to clipped/limited material (sub-band energy distribution, not just peakiness) — flagged as Story 4.5 BNNS dev-note (Epic 3 retro 2026-05-03)
