## Intent

**Problem:** Progressive retry (intensity 6+) analyzes multiple time windows (30s, 60s, 90s) but discards all candidates except the highest-confidence single window. A 30s window may surface a correct candidate that the 90s window misses (or vice versa), but this information is thrown away. 11 of 30 OA300 Acc1 failures have the correct BPM absent from the top candidates entirely -- merging across windows could recover some of these.

**Approach:** Introduce a `CandidateMergeStrategy` enum with pluggable strategies (maxConfidence, dedup, quorum, average, median, weightedAverage, union) so different merging heuristics can be tested via ablation. Collect candidates from all analyzed windows (intensity 6+), apply the selected strategy, and return the merged result. Default strategy is `maxConfidence` (preserves current behavior). Levels 1-5 unchanged.

## Boundaries & Constraints

**Always:**
- Candidates from each window are independently generated by `BPMAnalyzer.estimateBPM` (no changes to the core DSP pipeline)
- `maxConfidence` strategy uses the same selection logic as previous behavior (pick highest-confidence window); results may differ because all windows are now evaluated rather than early-exiting
- Merged candidate list is capped at `techniqueSet.candidateCount` after strategy application
- Levels 1-5 behavior is identical to current (single window, no merging)
- All existing tests pass without modification

**Ask First:**
- If merged results show Acc1 regression on OA300 vs current behavior

**Never:**
- Change `BPMAnalyzer.estimateBPM` internals or the DSP pipeline
- Add new DSPTechnique cases
- Change the public `AudioAnalysisResult` struct shape

## Design Notes

**Near-match clustering:** Two candidates are "near-matches" if `abs(a.bpm - b.bpm) / min(a.bpm, b.bpm) <= 0.02` (same 2% tolerance used for Acc1 matching). All strategies use this same clustering. Within a cluster, the BPM value used is from the highest-scoring entry.

**Score comparability:** Scores from different window lengths are not directly comparable (absolute magnitudes differ). `dedup` and `quorum` avoid this by using max-score or count-based ranking. `average` and `median` operate on scores within a cluster, which is acceptable for relative ranking even if absolute values differ. `weightedAverage` uses window confidence as the weight, so a high-confidence short window outweighs a low-confidence long one. `union` sidesteps the issue entirely -- just pools and sorts by raw score.

**Early exit removal for 6+:** The current early-exit (confidence threshold, convergence) is removed for intensity 6+ to ensure all windows contribute candidates. This makes 6+ slightly slower but enables the merge strategies to work with complete data. The performance cost is bounded (at most 3 windows).

**Confidence after merge:** For all strategies, confidence = `max(confidence)` across all windows that contributed candidates to the winning cluster.
