# Story 10.4: LUFSReadoutView — primary integrated LUFS + secondary breakdown

Status: done

## Story

**As a** demo user comparing tracks for loudness alongside BPM,
**I want** a clean LUFS panel showing integrated loudness as the primary number with true-peak and loudness range as secondary context,
**So that** loudness surfaces without competing with the BPM-centric flow.

This is a **demo-only** story (`Demo/BoomBoomBoomBPM/`, develop-only). `Sources/` and `Tests/` MUST stay byte-identical. **Two epic-AC premises are factually wrong and are corrected as recorded design decisions below (the mandatory pre-spec factual-claims grep — the same class of error caught in 10.2's `allEntries()` and 10.3's DD1):**
- **The demo computes NO LUFS today, and no result object carries it.** The epic AC's "an `AudioAnalysisResult` carrying a non-nil `LUFSReport`" does not exist — `AudioAnalysisResult` has no LUFS field, and `CombinedAnalysisResult` (what the demo threads) is explicitly documented "Scope: BPM + beat grid only — no LUFS" (`AudioAnalysisService.swift:86`). `LUFSReport` is produced ONLY by the standalone `analyzeLUFS(...)` call, as an Optional. So this story must **wire the `analyzeLUFS` call into the analysis task and store the report** — not merely render one already flowing (DD1/DD3).
- **True-peak is never `nil`; LRA is the sole optional field.** The epic AC's "true-peak unavailable for a particular sample rate → `True peak: unavailable`" is wrong: `maxTruePeakDBTP` is a non-optional `Double`, and the unsupported-sample-rate case is a *thrown* error, not a nil field. The genuinely-optional field is `loudnessRangeLU: Double?` (nil when the gated programme is < 60 s), so the labeled-fallback AC targets **LRA** (DD2).

### What this story is (and is NOT)
It IS: (a) a NEW `LUFSReadoutView` rendering integrated LUFS as the primary number with true-peak + LRA as labeled secondary context, and (b) the wiring that first brings LUFS into the demo (a best-effort `analyzeLUFS(url:)` call in the existing detached analysis task + a `lufsReport` property). ### Recorded design decisions (flag at PR, mirroring the 9.x / 10.1 / 10.2 / 10.3 precedent)
- **DD1 — no result object carries LUFS; the demo computes none today.** The epic AC says "an `AudioAnalysisResult` carrying a non-nil `LUFSReport`" — factually wrong (same class as 10.2's `allEntries()` and 10.3's DD1). `AudioAnalysisResult` has fields `bpm`/`confidence`/`candidates`/`trace`/`metadataEvidence`/`effectiveIntensity`/`degradationReason` — no loudness. `CombinedAnalysisResult` (returned by `analyze(...)`, the demo's actual call) holds only `bpm`/`beatGrid` and is documented "Scope: BPM + beat grid only — no LUFS (DD #1)" (`AudioAnalysisService.swift:86-88`). A `grep` for `LUFS|Loudness|dBTP|truePeak` across all of `Demo/` returns zero hits — the demo has never surfaced loudness. `LUFSReport` is returned ONLY by `analyzeLUFS(url:options:) throws -> LUFSReport?` (`AudioAnalysisService.swift:1317`) or the shared-decode `analyzeLUFS(decoded:options:)` (`:1370`), as an **Optional**. So the story wires the call and stores the report (AC1).
- **DD2 — true-peak is never `nil`; LRA is the ONLY optional stored field.** The epic AC #4 example ("true-peak unavailable for a particular sample rate") is wrong: `maxTruePeakDBTP` is a non-optional `Double`; unsupported sample rates (anything but 44.1/48/96 kHz) surface as a **thrown** `LUFSAnalysisError.unsupportedSampleRate`, not a nil field. The genuinely-optional field is `loudnessRangeLU: Double?` (nil when the gated programme is < 60 s or the gated set is empty; the library's own `description` renders it `"n/a"`). So the labeled-fallback AC (AC4) targets LRA: `Loudness range: unavailable`. When LRA is nil, `lraLowLUFS`/`lraHighLUFS` are the `-100.0` sentinel — do not render them as a band. (The story shows scalars only, so band-drawing is moot, but the sentinel guard in the formatters still matters for defensive display.)
- **DD3 — best-effort separate `analyzeLUFS(url:)` call, mirroring the waveform decode (NOT a shared-decode refactor).** The demo's detached task already pays a URL-path `analyze()` decode plus a separate best-effort `Waveform.decode(url:)`.
