# Story 8.5a: Downbeat detection — fixed-meter downbeat-phase estimation

Status: done

## Story

As a **library consumer** (concretely: a Rekordbox-style DJ app doing bar/half-bar quantized launch),
I want **`DownbeatResult.detected` populated with a first-downbeat anchor + the assumed meter when the rhythmic evidence is strong enough, and an honest `.noneDetected` abstain otherwise**,
so that **I can extrapolate bar lines (`anchorTime + barIndex × beatsPerBar / (tempo/60)`) and snap launches to the top of the bar — without the library ever fabricating a downbeat it isn't sure of.**

## ⚠️ Context (read FIRST)

This is a **quick follow-up to Story 8.5** that fills the gap flagged in 8.5 DD #13: `DownbeatResult` (the public tri-state from Story 8.3) is `.notAttempted` everywhere and **no story populates it**, which blocks the DJ consumer's bar/half-bar (1/1, 1/2) snap. This story adds a conservative, pure-DSP downbeat-*phase* estimator on top of the beats the 8.5 grid already produces.

- **Hard dependency on Story 8.5.** This story consumes `BeatGrid.gridOrigin: BeatGridAnchor?` and sets `BeatGridAnchorSource.downbeat` (both introduced in 8.5). Sequence: 8.5 → 8.5a. It does NOT touch the BPM pipeline or the C2 octave logic.
- **Scope is deliberately narrow (Codex thread `019ec2a4`).** Assume **4/4** (carry `beatsPerBar` as `.assumed`, do NOT pretend to detect meter); estimate a **single downbeat phase** (which beat-in-bar is beat 1); produce a **first-downbeat anchor** + the downbeat beats; **abstain** (`.noneDetected`) when evidence is weak. A wrong downbeat on a live deck is worse than no downbeat — the success condition is "produce a downbeat when the rhythmic evidence is strong; otherwise abstain", NOT "always produce one".
- **Clean-room / aubio fence (KDD-C1, project rule).** No aubio source transcribed or named in code/public PRs. Cite academic literature for the metrical-accent heuristic (DD #7).
- **Constant-tempo only** (inherited from the fixed-period tracker; 8.4 doc). Variable meter / non-4/4 detection / per-beat `Battito` are explicitly out of scope (DD #8).

## Acceptance Criteria

**AC1 — `MeterEstimate` + enriched `DownbeatResult.detected` payload (public types).**
Add `public struct MeterEstimate: Sendable, Hashable, Codable { public let beatsPerBar: Int; public let source: MeterSource }` and `public enum MeterSource: Sendable, Hashable, Codable { case assumed; case detected }`. **Enrich** `DownbeatResult.detected(beats: [BeatTimestamp])` → `case detected(estimate: DownbeatEstimate)` where:
```swift
public struct DownbeatEstimate: Sendable, Hashable, Codable {
  public let beats: [BeatTimestamp]   // the downbeat beats (bar starts), in order
  public let meter: MeterEstimate     // { beatsPerBar: 4, source: .assumed } in 8.5a
  public let confidence: Float        // [0,1], clamped finite (NaN-free → Hashable)
  public let phaseIndex: Int          // which beat-in-bar (0..<beatsPerBar) is the downbeat
}
```
The associated value stays **labeled** (`estimate:`) to keep the `Codable` wire-shape stable (`{"detected":{"estimate":{…}}}` not `_0`) — same rationale as the existing `beats:` label (Story 8.3 DD #9 / SE-0295). `DownbeatResult` remains NOT `CaseIterable` (associated value), `Hashable` sound (all floats clamped finite). `BeatGridTypesTests` updates to the new payload (BC not a goal). `DownbeatResult.description` switch stays exhaustive (no `default:`).

**AC2 — opt-in downbeat detection; default path unchanged.**
Add `Options.detectDownbeats: Bool = false`. When `false` (default), `BeatGrid.downbeats == .notAttempted` exactly as today — the BPM/beat-grid output is byte-identical to 8.5 (`.bitPattern`-locked). When `true`, the grid path runs the downbeat estimator and sets `downbeats` to `.detected(estimate:)` or `.noneDetected`. The combined `analyze(...)` and both `analyzeBeatGrid` overloads honor it.

**AC3 — downbeat-phase estimator (fixed 4/4, percussive-accent heuristic).**
A new internal estimator (`DownbeatAnalyzer` or a method on `BeatGridAnalyzer`) runs over the detected beats + the per-frame sub-band onset envelopes (`OnsetEnvelopes.subBands = [kick, snareLow, snareCrack, hiHat]`, declared at `BPMAnalyzer.swift:671`; the four band ranges are `BPMAnalyzer.swift:140-143`, so `lowBand = subBands[0]` (kick, `0..<20` ≈ 30–200 Hz) and `snareCrack = subBands[2]` (`50..<80`)) when `detectDownbeats == true`:
1. For each detected beat (window-relative frame `f`), sample a window of `±20%` of the beat period around `f` and take the per-band peak from kick (low / `subBands[0]`), snareCrack (`subBands[2]`), and full-band envelopes; **peak-divide-normalize** each band across the analysis window: `bandNorm[i] = band[i] / max(ε, vDSP.maximum(band))` with `ε = 1e-6` (Float), so every band lands in `[0, 1]` (NOT z-score — z-score emits negatives that collide with the `clamp ≥ 0` in step 2 and would silently zero half the signal).
2. Per-beat downbeat-likelihood `score = 1.0·lowBand + 0.25·fullBand − 0.25·snareCrack`, clamped `≥ 0` (low-frequency/kick emphasis marks bar starts; subtract snare-crack to suppress backbeat phases — DD #7).
3. Assign each beat a **bar-phase index by quantized POSITION, NOT array index**: `phase = Int(((beatTime − firstBeatTime) / beatPeriod).rounded()) % beatsPerBar`, where `beatPeriod = 60.0 / estimatedTempo`. Folding by raw array index (`i % beatsPerBar`) is unsound — the Davies & Plumbley DP backtrace admits inter-beat intervals in `[period/2, 2·period]`, so it can drop or double a beat mid-window (the exact hazard 8.5 DD #4 names), and one dropped/doubled beat shifts every later array-index phase by ±1, scrambling all bins. Position-quantization is robust to a single missing/extra beat. **Grid-integrity abstain:** if the beat array is non-uniform — consecutive inter-beat intervals deviate from `beatPeriod` by more than **0.25** (25%, pinned — not `~`) for more than **20%** of the inter-beat intervals (the DP lost the grid) — return `.noneDetected` rather than estimate a phase from an unreliable grid. (Both constants are pinned because AC8(i)/(i′) branch directly on them; a single dropped/extra beat in a ≈15-bar default window is ≈1.7% of intervals, well under 20%, so it does NOT trip this guard — position-quantization (this step) handles it. The guard fires only when the DP genuinely shredded the grid.)
4. Aggregate each of the `beatsPerBar` phase bins with a **median (or trimmed mean), NOT a raw sum** (a single transient must not dominate — Codex; AC8(g) depends on the median rejecting a one-bar bass-drop a raw sum would be fooled by). Median is the intent; a high-trim trimmed mean is an acceptable vDSP-amenable substitute. **This per-bin reduction is over ≈`bars` values across only `beatsPerBar ≤ 4` bins — O(beatsPerBar)-small, and its sort is explicitly EXEMPT from AC7's no-per-beat-heap rule** (that rule targets the per-beat sampling loop of step 1, not this tiny fixed-width bin reduction). Winner = max-aggregate phase bin; the first downbeat = the **earliest detected beat whose bar-phase == the winner phase**; the downbeat beats = all detected beats whose bar-phase == the winner phase, within coverage.

**AC4 — honest confidence + abstain path.**
`confidence = 0.7·margin + 0.3·separation`, where `margin = clamp01((winner − runnerUp) / max(winner, ε))` and `separation = clamp01((winner − meanPhaseScore) / max(winner, ε))`, with `ε = 1e-6` (Float). (The confidence term is named `separation` — distinct from gate (d)'s multi-bar *support* below; they are different quantities.) The estimator retains **both** the per-phase aggregate (for `winner`/`runnerUp`/`meanPhaseScore`/`margin`/`separation`) **and** the winner phase's per-bar score vector (for gate (d)). Return `.detected(estimate:)` **only if all** hold: (a) `≥ 3` complete bars of beats exist (`beats.count ≥ 3·beatsPerBar`); (b) `winner > 0` **and** `winner ≥ 1.25 · runnerUp` (the `winner > 0` guard keeps the margin gate self-sound — an all-zero histogram must not pass on `0 ≥ 1.25·0`); (c) `confidence ≥ 0.4`; and (d) **multi-bar support** — the winner phase's per-bar score exceeds the per-beat mean in `≥ ceil(bars/2)` bars (a real recurring accent, not a single-bar spike). Otherwise return `.noneDetected`. (Conservative by design — a missed downbeat just disables bar-snap; a wrong one causes audibly wrong launches.)

**AC5 — `gridOrigin.source == .downbeat` on success; preserved on abstain.**
When the estimator returns `.detected`, the grid's `gridOrigin` (from 8.5) is set to the **first downbeat** with `source == .downbeat` (the reserved 8.5 case). When it returns `.noneDetected` (or `detectDownbeats == false`), `gridOrigin` keeps the 8.5 phase-consistency anchor (`source == .medianConsistentBeat` / `.strongestBeat` / `.firstBeat`) unchanged. This is what lets the DJ consumer phase the bar grid off `gridOrigin` only when `source == .downbeat`.

**AC6 — sub-band onset envelopes forced when downbeats requested (no BPM perturbation).**
Sub-band onset envelopes are currently computed only when `techniqueSet.contains(.subBandVoting)` (`BPMAnalyzer.swift:264,270`). When `detectDownbeats == true`, the grid path **forces `computeSubBands: true`** so the estimator has its input, independent of the active technique set. This is additive — the sub-band envelopes feed only the downbeat estimator (and sub-band voting iff that technique is independently on); the **BPM selection result is unchanged** (`.bitPattern`-locked, AC2).

**AC7 — performance.**
With `detectDownbeats == false`: zero added cost (byte-identical, AC2). With `detectDownbeats == true`: the added cost is one sub-band onset pass (if not already computed for `.subBandVoting`) + an O(beats) folding pass — reported, not gated to a fixed ceiling (mirrors 8.5 AC10). The estimator allocates no per-beat heap in a loop where a vDSP primitive serves (CLAUDE.md). The O(beatsPerBar)-bin median aggregation (AC3.4) is exempt — it is a fixed-width (`≤ 4`-bin) reduction, not a per-beat loop.

**AC8 — tests.**
`DownbeatAnalyzerTests` (deterministic, runtime-generated fixtures): (a) a synthetic 4/4 click with a **kick emphasized on beat 1** every bar → `.detected` with `phaseIndex` matching the planted downbeat and `gridOrigin.source == .downbeat`; (b) a **flat four-on-the-floor** click (equal kick every beat) → `.noneDetected` (abstain — no phase separation); (c) **fewer than 3 bars** → `.noneDetected`; (d) `detectDownbeats == false` → `.notAttempted` + BPM byte-identical (`.bitPattern`); **(d′)** `detectDownbeats == true` on a track where the estimator abstains → BPM result `.bitPattern`-identical to the `detectDownbeats == false` run — **this is the test that actually locks AC6's forced-`computeSubBands` byte-identity; (d) alone never exercises the forced sub-band path** (the `false` path computes sub-bands only if `.subBandVoting` is independently on); (e) `DownbeatResult`/`DownbeatEstimate`/`MeterEstimate` `Codable` round-trip + the labeled `estimate:` wire-shape + NaN-free `Hashable`; (f) **backbeat-heavy** click (snareCrack on phases 1&3, equal kick everywhere) → the `−0.25·snareCrack` penalty must NOT promote a snare phase as downbeat (abstain or pick the true kick phase, never a backbeat phase) — exercises the backbeat mitigation; (g) **bass-drop** fixture (one bar with a huge low-band transient on a non-downbeat phase) → the median aggregation rejects it where a raw sum would be fooled — exercises the AC3.4 median mitigation; (h) **anacrusis** (a strong accent on the pre-bar-1 pickup beat) → the multi-bar support gate (AC4d) holds against the single-beat pickup; (i) **one planted missing beat** mid-window, with the gap kept **under** the AC3.3 grid-integrity threshold (1 missing interval out of ≈60 beats ≈ 1.7% < 20%) → the position-quantized folding (AC3.3) resolves to the **planted phase** — assert that single outcome, NOT a scrambled phase (no "OR" in the assertion); **(i′)** enough planted missing beats to exceed the 20% grid-integrity fraction → `.noneDetected` (the abstain branch, asserted separately so each fixture has exactly one correct answer). Assertions use **independent ground truth** (the planted downbeat phase), never the estimator's own output.

**AC9 — `BeatGrid.schemaVersion` semantic-contract stamp (rides this story's `Codable` break).**
Add `public let schemaVersion: Int` to `BeatGrid` with `public static let currentSchemaVersion = 1`. The memberwise init gains `schemaVersion: Int = BeatGrid.currentSchemaVersion` (**defaulted**, so every producer call site auto-stamps the current version and **no existing construction site changes**); `with(tempoAgreement:)` forwards the instance's `schemaVersion` (W52 forward-every-field — a decoded-then-restamped grid keeps its original version). `init(from:)` decodes it via `try container.decodeIfPresent(Int.self, forKey: .schemaVersion) ?? 1` — **faithful decode: it stores whatever integer it reads (including an unknown future value) and NEVER throws on an unrecognized version** (matching the in-repo stored-version precedent `BaselineRecord.schemaVersion: Int` in `PerformanceBenchmarkTests`, which warns-and-skips rather than throwing, and `BeatGrid.init(from:)`'s decode-faithfully-then-route-through-the-clamping-init doctrine). The synthesized `encode(to:)` writes it **always**; `CodingKeys` is synthesized so the field auto-extends it. `Int` keeps the NaN-free→`Hashable` doctrine untouched (no clamp site — same Int-vs-Double reasoning the design notes §1 use for the octave factor); it is **not** range-validated (a malformed negative decodes as-is — the consumer gates, the library does not). DocC documents three things: **(i)** what it identifies — the persisted `BeatGrid` *semantic* contract over the top-level fields AND the nested graph (`BeatTimestamp`/`BeatGridAnchor`/`BeatGridCoverage`/`TempoAgreement`/`DownbeatResult`); **(ii)** the **read-side consumer contract** — *a consumer that caches the raw `BeatGrid` should compare `schemaVersion` against `currentSchemaVersion` (or the version its cache was written under) and re-index on mismatch; the library does NOT migrate old grids*; **(iii)** the **bump-trigger list** — bump on a `confidence`-formula change, an `estimatedTempo`/`presentationTime` provenance/units change, a `tempoAgreement` factor-sign change, or a nested-enum meaning change; **do NOT** bump for pure accuracy improvements that preserve the contract. README "## Beat grid" gains one sentence on the field's purpose. It is **not** sold as cache protection or backwards compatibility (it is neither — see DD #9); it is a semantic-drift/forensic stamp the consumer may gate on. Tests (in `BeatGridTypesTests`): a legacy payload WITHOUT the key decodes to `schemaVersion == 1` (absent→1); the encoder always emits the key; an unknown future version (e.g. JSON `"schemaVersion": 99`) decodes to `99` with no throw (faithful decode); two grids differing only in `schemaVersion` are unequal and hash differently (it is a real field); `with(tempoAgreement:)` preserves a non-default `schemaVersion`; and an **explicit `currentSchemaVersion == 1` contract assertion** (plus a default-constructed `BeatGrid` carrying `schemaVersion == 1`) — this pins the current version so a future bump is a **visible diff against a test**, not a silent edit (the closest an inert field gets to enforcement — it does not replace the bump-trigger DocC discipline, it backstops it).

## Dev Notes

### Design Decisions (DDs)

**DD #1 — fixed-meter downbeat-PHASE estimation, not general downbeat tracking (Codex).** The honest framing: estimate which beat-in-bar is beat 1 for **percussive, constant-tempo, 4/4** material. Do not claim general downbeat detection. The MVP is a metrical-accent heuristic with an abstain path, not an ML/DBN/particle-filter system (those are explicitly what we are NOT doing — DD #7).

**DD #2 — `beatsPerBar` is `.assumed`, never pretend-detected (Codex).** Carry `MeterEstimate { beatsPerBar: 4, source: .assumed }`. Do NOT hardcode `4` internally without surfacing that it is assumed — a consumer must know the meter wasn't measured. Non-4/4 detection is a later story; `MeterSource.detected` is reserved for it.

**DD #3 — enrich `DownbeatResult.detected` now (Codex; BC not a goal).** The current `.detected(beats:)` is too thin for a consumer deciding whether to trust bar-snap — it carries no meter, confidence, or phase. Change to `.detected(estimate: DownbeatEstimate)` while pre-1.0. Keep the associated value **labeled** for a stable `Codable` wire-shape (Story 8.3 DD #9). A future per-beat `Battito` payload is additive (`DownbeatEstimate` gains an optional `beatPositions: [BeatPosition]?` later — no breaking change). This is consistent with how 8.5 reshapes `BeatGrid` (nothing shipped to `main`).

**DD #4 — opt-in, default-off, BPM byte-identical (AC2/AC6).** `Options.detectDownbeats = false` keeps `downbeats == .notAttempted` and the BPM result `.bitPattern`-identical. Forcing `computeSubBands: true` when downbeats are requested is additive: sub-band envelopes feed the downbeat estimator only; they alter BPM selection **only** via `.subBandVoting`, which is independent and unchanged. Lock BPM byte-identity in a test (AC8d).

**DD #5 — runs in the window-relative frame space the beats were tracked in.** The detected beats' window-relative frames `f` (the same `f` 8.4 used to compute `presentationTime = (windowStartSample + f·hopSize)/sampleRate` and `strength = onsetEnvelope[f]/envMax`) index directly into `subBands[band][f]`. Run the estimator alongside `estimateBeatGrid` (or pass the beats' frame indices) so no track↔window offset reconciliation is needed. The default `.analysisWindow` coverage (≈30 s) already yields many bars (30 s @ 120 BPM = 60 beats = 15 bars ≥ the 3-bar floor), so downbeat detection works on the cheap default coverage.

**DD #6 — NO trace field; KDD-T0 does not trigger (carries over from 8.3/8.4/8.5).** Downbeat output rides `BeatGrid.downbeats`, a parallel result, not a `UnifiedSignalPool` participant. No `BeatGridTraceEntry`/trace field; 5-recipe audit zero matches; W74 stays armed.

**DD #7 — academic grounding (aubio fence held).** The metrical-accent heuristic (low-frequency/bass + percussive accent marks bar starts) is grounded in academic literature, cited in DocC, NOT aubio: Goto's bass/drum-pattern beat-tracking; Klapuri, Eronen & Astola, "Analysis of the meter of acoustic musical signals" (hierarchical meter from accent features); Durand, Bello, David & Richard (downbeat tracking from rhythm + bass content — cited as the ML direction we deliberately do NOT take); Böck, Krebs & Widmer ("Joint Beat and Downbeat Tracking with Recurrent Neural Networks", ISMIR 2016 — RNN downbeat likelihood + dynamic Bayesian network temporal model; likewise the learned direction we are NOT taking); Davies & Plumbley (and Ellis's dynamic-programming beat tracking, 2007 — a separate work, not a single co-authored paper) ground the beat-phase/tempo side, not the downbeat classifier. Frame it as "fixed-meter downbeat-phase estimation for percussive constant-tempo music." Imports stay `Foundation` + `Accelerate`; `Package.swift` unchanged.

**DD #8 — explicit deferrals.** Out of scope (later stories, if ever): non-4/4 meter detection; per-beat `Battito` (1–4) labels; harmonic-change / section / phrase-level downbeats; full-track downbeat correction; ML/DBN downbeat models; variable-tempo bar tracking.

**DD #8a — real-audio fire-rate metric deferred (Codex tie-break, 2026-06-14).** The PM evidence pass flagged that 8.5a's acceptance is synthetic-only (AC8 planted-phase fixtures + AC7's ungated perf report) and therefore cannot catch a "so conservative the estimator never fires on real tracks" failure — there is no real-audio downbeat fire-rate/correctness number. Valid concern. Codex's adjudication: **defer it.** 8.5a's acceptance stays focused on deterministic correctness + abstain behavior; a reported (ungated) OA300 downbeat fire-rate metric — analogous to the existing `*-impact-report` benchmarks (`make beat-grid-impact-report` etc.) — is useful *once the estimator exists* but must not expand this already-mixed implementation story. Registered as a follow-up validation item in `deferred-work.md` (8-5a-D1). (Real-audio downbeat *correctness* additionally needs downbeat ground truth, which the OA300 BPM oracle does not currently carry — the follow-up story scopes that.)

**DD #9 — `BeatGrid.schemaVersion` lands here because 8.5a is the last unversioned shape (operator decision, Codex + 3-agent adversarial triangulation, 2026-06-14).** Recorded in full so a reviewer understands this is a deliberate, scoped, honestly-framed addition — not BC creep.
- **Why this story:** 8.5a already breaks `BeatGrid`'s `Codable` shape (the `DownbeatResult` reshape, AC1/DD #3). A caching consumer re-indexes on that decode regardless, so stamping `schemaVersion = 1` in the **same** change makes 8.5a the *last* unversioned `BeatGrid` shape at **zero marginal break**. Any later home (8.7 / its own story / "before 1.0") would spend a **second, gratuitous** cache-invalidation purely to introduce the seam, and leave 8.5a's shape as one more permanently-unversioned generation in consumer caches.
- **What it is — honest framing (NOT backwards compatibility, which is a non-goal [[feedback_no_bc_goal_prerelease]]):** a **semantic-drift / forensic stamp**. A *breaking* shape change already throws at decode (a renamed/removed required key fails `init(from:)` — exactly what 8.5a's `DownbeatResult` reshape does), so `schemaVersion` adds **nothing** there. Its **only** job is the orthogonal, narrow class the throw misses: a future change that keeps every key decodable but redefines **meaning** — the `confidence` formula (a documented stability contract, `BeatGrid.swift` confidence DocC + design-notes §3 makes the consumer's auto-sync gate depend on it), `estimatedTempo`/`presentationTime` provenance/units, or the `tempoAgreement` factor sign. On this type those are real surfaces.
- **What it is NOT — be direct:** it is **inert in-library**. Nothing in `Sources/` reads it. This is the load-bearing distinction from `MLFeatureFrames.featureSetVersion` (which the original §8 note mis-cited as the precedent): `featureSetVersion` is a *runtime* abstain seam `BNNSTechnique.evaluateWithDiagnostic` actively checks at `BNNSTechnique.swift:366` (abstains on mismatch) — it is load-bearing within one build; `BeatGrid.schemaVersion` is a value a *consumer* may gate on, read by no library code. It does **not** protect a cache — the consumer's own `cacheFormatVersion` over its owned projection does (design-notes §0/§8a), which makes the library field **redundant for the sole real consumer** if that consumer follows the cache-a-projection advice. It is justified as low-cost insurance for the semantic-drift class + forensics, explicitly **not** as compatibility or cache protection.
- **Coverage caveat (state it plainly):** a top-level `BeatGrid.schemaVersion` is a **hand-maintained assertion** that "something in the serialized graph changed" — NOT compiler-enforced, and it does not structurally witness a change *inside* a nested type (8.5a's own break lives inside `DownbeatResult`). Correctness depends entirely on bump discipline (the AC9 trigger list — same `MUST bump` human-checklist fragility `featureSetVersion` carries). Per-nested-type versions are explicitly NOT added (absurd churn, no consumer benefit).
- **`?? 1` honesty:** the absent→1 default means the field cannot retroactively tag grids cached *before* 8.5a (they decode as a genuine-looking v1); it only versions forward. Accepted — the alternative (no field) versions nothing.
- **Not write-only theater:** a version nobody is told to read is worthless, so AC9 ships the **read-side consumer DocC contract** ("compare against `currentSchemaVersion` / your cache's version; re-index on mismatch; the library does not migrate") alongside the field. The field's whole value is the consumer's ability to gate on it.
- **Shape:** bare `Int` (not a `featureSetVersion`-style `String`) — a cache-envelope version only needs ordered comparison; `Int` gives it free and stays `Hashable`-clean. Faithful decode, never throw (mirrors the `BaselineRecord.schemaVersion: Int` warn-and-skip precedent and `BeatGrid`'s decode-faithfully doctrine; the library cannot judge a future version's compatibility — only the consumer can).

### Failure modes + mitigations (from Codex; bake into the estimator + tests)

| Failure mode | Mitigation (in AC3/AC4) |
|---|---|
| Four-on-the-floor (kick every beat → flat low-band phase) | margin gate + abstain (AC8b is exactly this case → `.noneDetected`) |
| Backbeat-heavy (snare/clap on 2 & 4 dominates) | `− 0.25·snareCrack` term penalizes snare-heavy phases |
| Breakbeat/DnB (kick avoids beat 1 / implies half-time) | abstain on low margin; constant-tempo + half-time is the BPM stage's octave concern |
| **Steadily syncopated / displaced-kick (reggaeton/dembow, UK garage — kick deliberately off the downbeat *every* bar, not a one-off)** | the realistic 4/4 percussive case most likely to fool `1.0·lowBand` — distinct from the one-bar bass-drop/breakbeat rows (those are disruptions, this is a *steady* pattern). Relies on the margin gate (AC4b) + multi-bar support (AC4d) to abstain rather than lock a wrong phase; **documented limitation, not corrected** (DD #8). Flagged by the analyst evidence pass 2026-06-14. |
| Pickups / anacrusis (first phrase accent ≠ bar 1) | multi-bar support requirement (AC4d) |
| Bass drop / fill (one bar-local event) | median/trimmed aggregation (AC3.3), not raw sum |
