# Story 10.5: HelpButton + strategy popovers wired to Epic 11 docs

Status: reverted-deferred

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

> **REVERTED to baseline — deferred to Epic 11 (2026-07-12, operator + Codex `gpt-5.6-sol` thread `019f543c`).** Story 10.5 built, reviewed (clean), and shipped the generic `HelpButton` + `@Entry docsResolver` FR-42 seam — then, in live GUI testing, every call site proved either **redundant** with an existing always-visible inline subtitle (merge strategy; ensemble was already superseded by 9.1), **confusing** (the DSP-technique chips read as interactive), or **already covered** by the pre-existing graph-legend popovers (`BeatGridHelpButton`/`LoudnessHelpButton`). Conclusion (Codex, endorsed by operator): the story was **prematurely sequenced** — a generic docs-popover only earns its place once Epic 11 ships the multi-paragraph authored prose that a popover-on-demand beats an inline one-liner for. The **entire 10.5 implementation was reverted** (demo byte-identical to baseline `b57ff0e`); the design pattern + UX rules are preserved in `_bmad-output/implementation-artifacts/fr42-demo-popover-design-note.md` for an **Epic 11 demo-integration story**, where the mechanism gets wired to real docs. FR-42 moves to Epic 11. This spec is retained as the audit record; the sections below describe the (now-reverted) implementation. "Not lost work — course correction."

> **Post-ship scope trim (2026-07-12, operator-directed after live GUI test).** The read-only "Active DSP techniques" chip readout **shipped then was removed**: in live testing it read as interactive (chips looked like toggles/activation indicators) — the exact "pills-read-as-clickable" risk both Codex and the party-mode UX voice had flagged. Operator directed removing it entirely, reverting to **Codex's original merge-strategy-only recommendation**. **AC5** (readout) and **DD3** (readout derivation) are **RETIRED**; **AC7** is now scoped to the `MergeStrategyDoc` family only (8 cases). What remains is the story's real deliverable — the generic `HelpButton<T: DemoDocumentedCase>` + `@Entry docsResolver` FR-42 seam — wired to the **Merge strategy** control (its one shipped call site). `DSPTechniqueDoc`, `DSPTechniquesReadout`, `TechniqueChip`, and their tests were deleted; `Sources/`/`Tests/` remain byte-identical. See the Change Log.

## Story

As a **demo user exploring the analysis controls**,
I want **a "?" button beside the strategy controls that opens a popover explaining what each option does — even before the authored docs bundle ships**,
so that **I can understand `.maxConfidence` vs `.windowVoting`, or what "vote/fine/sharp" techniques the current intensity turns on, without leaving the app.**

> **Scope reconciliation (2026-07-11, create-story + Codex `gpt-5.6-sol` consult + operator decision).** The epics.md Story 10.5 AC (`epics.md:1491-1521`) names three *example* controls — "ensemble preset / DSP technique / merge strategy." Two of those do not match the **shipped** demo and are **non-goals** here (see DD1): (a) the **ensemble-preset** control already carries an intentional inline per-selection description from Story 9.1 that supersedes a popover for it (`EnsemblePresetPicker.swift:36-39`); (b) there is **no user-facing DSP-technique control** — only the intensity slider, which maps intensity→`TechniqueSet` internally. **Operator decision:** wire the generic HelpButton to the **Merge strategy** control, and add a **read-only `TechniqueSet` readout** (which DSP techniques the current intensity activates) that carries per-technique popovers — surfacing DSP-technique docs **without** adding a new mutable control or disturbing the intensity→`TechniqueSet` model. The two existing pane-legend buttons (`BeatGridHelpButton`/`LoudnessHelpButton`) are a **different concern** (visual-legend explainers, already pane-context-switched in `ContentView`) and are **left untouched** (DD5). This story's real deliverable is the reusable generic `HelpButton<T: DemoDocumentedCase>` + the FR-42 graceful-degradation seam. The two wired call sites demonstrate it across the **currently-surfaced** cases: all **8** `BPMSelectionPolicy` merge strategies (fully reachable via the Picker) plus the **intensity-reachable** `DSPTechnique` subset — which is only **3** today (`acfSharpening`, `subBandVoting`, `fineGridRefinement`), because `AnalysisIntensity.techniqueSet` maps level 1→empty, level 2→`.baseline` (vote+fine), levels 3-10→`.optimal` (sharp+vote+fine); the other 5 techniques never surface via the intensity control. The `DSPTechniqueDoc` descriptor is **exhaustive over all 8** `DSPTechnique` cases — **not** speculative forward-compat, but because a `switch` over a `CaseIterable` library enum is **compiler-mandatory exhaustive** (you cannot author 3 arms and omit 5; the build fails). So all 8 get a one-liner because the language requires it; the `.allCases` test (AC7) simply guards that a future enum case can't land without one. Only the intensity-reachable subset is *displayed*.

## Acceptance Criteria

**AC1 — generic HelpButton + demo-local descriptor protocol (FR-42; demo-owned, zero Epic-11 compile dependency).**
**Given** `DocumentedCase` is a **library** protocol that Epic 11's Story 11.1 will declare (KDD-E1 caps that family at one protocol, pre-1.0) and Epic 10 must **NOT** compile-depend on it,
**When** `Demo/BoomBoomBoomBPM/BoomBoomBoomBPM/HelpButton.swift` is implemented,
**Then** it declares a **demo-local** descriptor protocol `DemoDocumentedCase` (distinct from the library `DocumentedCase`) exposing `var docID: String` and `var shortDescription: String`, and `struct HelpButton<T: DemoDocumentedCase>: View` taking a `case: T` parameter, rendering an SF Symbol `questionmark.circle` button (mirroring the shipped `BeatGridHelpButton` chrome: `.buttonStyle(.borderless)`, `.controlSize(.small)`, a `.help(…)` tooltip). The demo protocol is bridged to Epic 11 **only by the string `docID`**, NEVER by a shared type — a future dev must NOT make a library enum conform to `DemoDocumentedCase` (Epic 10 party-mode decision, 2026-07-07). Concrete conformers are **demo-owned adapters** (DD2/DD3), not library-type conformances.

**AC2 — injected docs resolver seam (Codex-flagged compile-safety; the FR-42 mechanism).**
**Given** the Epic 11 accessor `BoomBoomBoomKitDocs.attributedString(for:id:)` **does not exist yet** (unshipped) — so a *literal* reference to it would fail at **compile** time, not degrade at runtime,
**When** the popover resolves its content,
**Then** resolution goes through a **single, demo-local injected resolver** of type `DocsResolver` (`typealias DocsResolver = @Sendable (String) -> AttributedString?`), supplied via a SwiftUI environment value `docsResolver` declared with the **`@Entry` macro** (`@Entry var docsResolver: DocsResolver = HelpButtonDocs.absentDocsResolver` in an `EnvironmentValues` extension — NOT the legacy `EnvironmentKey`-conformance boilerplate) **whose default value is the absent resolver** (`{ _ in nil }`). Epic 10 never overrides it (so the whole demo runs on the absent resolver); Epic 11 later overrides it **once** at the app root (`.environment(\.docsResolver, …)`) with a resolver that calls the real library accessor — that single line is the `// EPIC 11 SEAM:`. **Seam contract (so Epic-11 wiring is one obvious line):** the demo `docID` is a single `"<kind>/<id>"` string (e.g. `"BPMSelectionPolicy/maxConfidence"`); the real accessor is `BoomBoomBoomKitDocs.attributedString(for kind: String, id: String) -> AttributedString` (**two args, NON-optional** — `architecture.md:624`), so the Epic-11 resolver splits the `docID` on the first `/` into `(kind, id)` and wraps the non-optional return. Because that accessor never returns nil, **the demo's shortDescription+Link fallback is dead once Epic 11 is wired — by design** (FR-42 graceful degradation is the *Epic-10-only* affordance; the library owns its own informative fallback thereafter). Do NOT file the fallback as dead code. `HelpButton` reads the resolver from `@Environment(\.docsResolver)` and exposes **no** resolver parameter of its own — tests never instantiate the view; they drive the pure `content(for:resolver:)` helper with a stub resolver directly (below). The literal `BoomBoomBoomKitDocs.attributedString(...)` symbol appears in **no compilable code** in Epic-10 demo Swift sources — it occurs only inside the `// EPIC 11 SEAM:` wiring guide + doc-comments (verify: `grep -rn BoomBoomBoomKitDocs Demo/BoomBoomBoomBPM/BoomBoomBoomBPM/*.swift` matches only comment lines). The **ironclad** proof of zero compile-time Epic-11 dependency is that the demo **builds** while `BoomBoomBoomKitDocs` is absent from `Sources/` entirely (grep-provable). The fallback path is unit-testable by injecting resolvers.

**AC3 — popover content + FR-42 graceful degradation.**
**Given** the user taps a "?" HelpButton,
**When** the `.popover()` modifier fires (KDD-D4 — SwiftUI `.popover()`, NOT a custom overlay, NOT a sheet, NOT a tooltip emulation),
**Then** the popover renders `resolver(case.docID)` **when non-nil** (the authored `AttributedString`); and **when nil** (Epic 11 unshipped or the id is unknown — FR-42) it falls back to a **two-element** view: (1) a one-line `Text(case.shortDescription)` (demo-authored on the descriptor, so the fallback needs nothing from Epic 11) and (2) a `Link("View docs on GitHub", …)` to the repo docs URL for that case (DD4 — label describes the destination, doesn't promise the page exists) — NOT a broken `Bundle.module` lookup, NOT an empty popover, NOT a crash, NOT a hidden button. The popover dismisses via SwiftUI's native `.popover()` behavior on tap-outside / `Escape` (KDD-D4 — no custom dismissal logic).

## Dev Notes

### What this story is (and is NOT)
It **IS**: (a) the reusable FR-42 infrastructure — a generic `HelpButton<T: DemoDocumentedCase>` + demo-local descriptor protocol + an **injected docs-resolver seam** + graceful-degradation fallback (short description + repo `Link`); and (b) two demonstration call sites — the **Merge strategy** control and a **read-only TechniqueSet readout** — covering the 8 reachable merge strategies plus the 3 intensity-reachable DSP techniques, backed by a tested 8-case DSP descriptor catalog. It is **NOT** a change to the library (`Sources`/`Tests` byte-identical, AC8), **NOT** a reversal of Story 9.1's ensemble inline description (DD1), **NOT** a new mutable DSP-technique control (DD1/AC5 — read-only readout only), and **NOT** a refactor of the two pane-legend buttons (DD5).

### Recorded design decisions (flag at PR, mirroring the 9.x / 10.1–10.4 precedent)

- **DD1 — reconciled scope vs the stale epic examples.** `epics.md:1501` names "ensemble preset / DSP technique / merge strategy" as popover targets; two are non-goals here. **Ensemble preset:** Story 9.1 shipped an intentional inline per-selection description (`EnsemblePresetPicker.swift:36-39` states it *supersedes* the 10.5 popover for that control) — reversing it is a UX regression, out of scope. **DSP technique:** no user-facing control exists (only intensity→`TechniqueSet`); manufacturing a mutable control "just to host help" is scope creep (Codex `gpt-5.6-sol` consult, 2026-07-11) that would need its own interaction ACs and reconcile against the intensity mapping. **Operator resolution:** merge-strategy popover + a **read-only** technique readout (surfaces DSP docs without a new control). `architecture.md:1100`/`:1237` still say `HelpButton<T: DocumentedCase>` (library protocol) — that predates the 2026-07-07 party-mode string-`docID`-bridge decision and is **stale**; follow the epics.md demo-local `DemoDocumentedCase` contract. Recommend a light epics.md AC + architecture.md touch-up (or defer to the party-mode finalize step) so the planning docs match this reconciled scope.
- **DD2 — merge-strategy descriptor is a demo-owned adapter, not library conformance.** `BPMSelectionPolicy` is a library enum; the AC forbids conforming it to the demo protocol. Wrap it in a demo `MergeStrategyDoc` adapter. Keep the existing inline `strategyDescription` caption (additive "?" — no regression). Seed `shortDescription` from `strategyDescription` so the two stay consistent.
- **DD3 — TechniqueSet readout is derivation-only + bounded to 3 reachable techniques. [RETIRED 2026-07-12 — the readout was removed post-ship per the top banner; the paragraph below describes the deleted design, kept as the audit record.]** The readout read `viewModel.options.intensity.techniqueSet.dspTechniques` live (intensity is already an `AnalysisIntensity` — no `rawValue` reconstruction); it adds no stored state and no mutation.
