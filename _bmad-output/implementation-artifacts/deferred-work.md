## Post-Disambiguation Merge Strategies

**Deferred from:** Merge strategy ablation (2026-03-27)
**Reason:** Ablation showed all clustering strategies hurt Acc1 vs maxConfidence

The 6 clustering-based merge strategies (dedup, quorum, average, median, weightedAverage, union) all perform worse than `maxConfidence` (59.8% vs 69.5% Acc1). Root cause: they merge raw candidates from `BPMResult.candidates` which are pre-disambiguation values. Each window's `BPMResult.bpm` has already been through sub-band voting and octave disambiguation, but the `.candidates` array contains the raw top-N peaks before that step.

To make merge strategies useful, they would need to operate on the *final disambiguated BPM* from each window rather than the raw candidates. This would mean:
1. Collect `(bpm: result.bpm, confidence: result.confidence)` from each window (post-disambiguation)
2. Cluster/vote on those final values
3. Return the winner

This is a fundamentally different approach from the current candidate-level merging.

**Files:** `CandidateMergeStrategy.swift`, `AudioAnalysisService.swift`
**Validation:** OA300 benchmark, targeting Acc1 > 69.5%

    - `RandomSample` — corpus sub-sampling for fast-cadence smoke benchmarks (analog to `make ablation-smoke`'s curated 16-combo subset). Currently the smoke list is hand-curated; a `randomSample(count:)` would change the determinism contract and is therefore **not** a drop-in.
    - `Combinations.allCombinations()` — `TechniqueSet.allDSPCombinations()` currently uses `2^7` bit-shift iteration (faster, clearer, locked by unit-test invariant `count == 128`). swift-algorithms `combinations(ofCount:)` returns subsets of a fixed size, NOT all subsets — wrong shape, no fit.
    - `Windows(ofCount:)` — sliding-window iteration. The DSP pipeline iterates window CHUNKS via vDSP indices; the multi-window candidate merge iterates `[BPMResult]`, not a sequence-window pattern. No load-bearing fit.
  - **Verdict:** none of the candidate sites is load-bearing enough to justify a dependency on its own. If a future story introduces N≥3 distinct usage sites (e.g., test-support utilities consolidating around `Grouped` + `Keyed` + `Product`), revisit then via a named story spec.

- **`swift-async-algorithms` — zero fit; do NOT adopt.** 3.6k stars. Modules cover async-stream composition (`Merge`, `Zip`, `CombineLatest`, `FlatMapLatest`), rate-limiting (`Throttle`, `Debounce`), buffering (`Buffer`, `MultiProducerSingleConsumerChannel`), reductions (`AsyncReductionsSequence`), timers (`AsyncTimerSequence`), and byte iteration (`AsyncBufferedByteIterator`). Surveyed against current code:
  - **Library is fundamentally synchronous.** `AudioAnalysisService.analyzeBPM(url:options:)` is a single throwing function. The DSP pipeline is sync end-to-end. The only async/await usage is the consumer-supplied `Task` that calls `analyzeBPM`, plus `withTaskGroup` for parallel track analysis in benchmarks (`AblationFullMatrixTests.fullAblationMatrix`, `OA300BenchmarkTests`). swift-async-algorithms does NOT replace `TaskGroup` — that remains stdlib territory.
  - **No async streams to compose.** The library has no `AsyncSequence` producers. Cancellation flows through the injectable `isCancelled: @Sendable () -> Bool` (synchronous predicate, default `Task.isCancelled`). Progress flows through `onProgress: (@Sendable (ProgressUpdate) -> Void)?` (synchronous callback). Both ADR-1 decisions explicitly prefer the synchronous predicate/callback model over `AsyncStream`.
  - **No event sources to throttle/debounce.** No UI events, no network streams, no file watchers — the library reads PCM once per `analyzeBPM` call.
  - **`AsyncBufferedByteIterator`** — irrelevant: `PCMBufferReader` uses `AVAudioFile` for audio decoding (Core Audio codecs), not raw byte iteration.
  - **Verdict:** zero candidate sites. swift-async-algorithms applies to event-driven / stream-oriented apps; this library is request-response synchronous. Do not investigate again unless the public API surface grows an `AsyncSequence`-shaped producer (e.g., a future "live BPM stream from microphone" use case — none currently planned).
