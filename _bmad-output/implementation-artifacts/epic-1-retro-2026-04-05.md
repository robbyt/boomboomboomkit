## Successes

- **Zero accuracy regression** across both stories. Buffer reuse and cancellation/progress were behavior-preserving. OA300 and GiantSteps benchmarks unchanged.
- **Buffer struct pattern** (PipelineBuffers, ACFBuffers, TempogramBuffers) established as a well-documented internal convention with allocate/deallocate/defer discipline.
- **Injectable closure pattern** for deterministic testing. `isCancelled` closure enables precise cancellation testing without timing-dependent flakiness.
- **Review quality improved dramatically** from Story 1-1 (8 findings, 5 patches) to Story 1-2 (0 actionable findings). Story-to-story learning is real.
- **GiantSteps infrastructure** built as a bonus during Epic 1, giving Epic 2 a head start.
- **Brownfield BMad adoption** process muscle built alongside real work. Good first epic establishing patterns.
- **`public init() {}` Options pattern** adopted -- single source of truth for defaults, no duplicated values between properties and init parameters.

## Challenges

- **Story 1-1 review was heavy:** 8 findings including a UB fix (vDSP_vclr vs pointer.initialize), assert vs precondition safety gap, and an unnecessary Array copy caught by Gemini cross-review.
- **Task 5 overscoped:** 12 candidates identified for `withUnsafeTemporaryAllocation`, only 1 converted (most return values escape scope). Investigation effort was disproportionate to yield.
- **Async test spec was racy:** Original spec used `Task` + 200ms delay; analysis completes in ~250ms. Caught during implementation, fixed with `withThrowingTaskGroup` + `cancelAll()`.
- **Access control visibility gotcha:** `PipelineBuffers` couldn't be `private` because `computeFourierTempogram` is test-accessible. Required `internal` instead.

## Key Insights

1. **Story-to-story learning works.** 1-1's review findings became 1-2's prevention -- the "Previous Story Intelligence" section in story specs is valuable and should continue.
2. **Brownfield BMad adoption is front-loaded.** Velocity should improve as process stabilizes.
3. **Tests are the primary quality signal** for a headless DSP library. Keep adding them aggressively -- no GUI to eyeball, so tests are how quality is measured.
4. **Multi-model cross-review** (e.g., Gemini) adds value on pointer-heavy/unsafe memory stories. Optional for higher-level service/API stories.
