## Intent

**Problem.** `BeatGrid` records only the requested `coverage` enum (`Sources/BoomBoomBoomKit/BeatGrid.swift:155-158`); the window the onset analysis actually covered and the length of the decoded, `maxSeconds`-capped buffer are computed in both producers and discarded (`BPMAnalyzer.swift:297-303`, `:677-694`), so no consumer can tell measured beats from extrapolated ones, and Hilbert's DTO already misstates its span as "about the first two minutes" when the default grid window is 30 s from the energy transition (`BPMAnalyzer.swift:113`). The canonical grid formula `gridOrigin.presentationTime + (60.0 / estimatedTempo) * n` (`BeatGrid.swift:20-21`) has no library implementation, so the demo (`Demo/.../BeatGridView.swift:465-490`) and Hilbert (its beat-mark renderer, `BeatMarks.swift:41-70` at Hilbert `d1f224b` per the guide's section 4.3; the file is not present in the sibling checkout as of 2026-10-23, so it is cited from the guide, not re-verified) each re-implement it with different guards. The bar-origin trust rule is stated two ways in this repo: `README.md:296` says gate on `source == .downbeat`, the type doc says `.downbeat` AND `.detected`, or `.manual` (`BeatGrid.swift:254-262`).

**Approach.** Two additive, independently landable parts, no DSP or timing change. Part A: a new optional stored field `BeatGrid.analysisSpan: BeatGridAnalysisSpan?` (integer sample bounds of the analyzed window, decoded sample count, sample rate), populated by both producers and nil for legacy and hand-built grids. Part B: a new public value type `PlayableBeatGrid` (constructible from an origin time and a BPM) with pure ordinal and time queries, a `BeatGrid.playableGrid` accessor, and a `BeatGrid.hasTrustedBarOrigin` gate. Two doc corrections ride along in files this story touches.

## Scope

**Out:** see "Out of scope" at the end. In short: no fitted tempo or phase in the public grid, no new enum case, no trace field, no edits beyond the existing two, no demo, nothing in Hilbert.

- Review follow-up (2026-10-23): `nearestBeat` now settles beyond DD-12's two-candidate wording. It starts at the floor of the position and walks to a neighbour while that neighbour's computed time is strictly nearer (up) or nearer-or-equal (down), at most 8 steps like the `beats(in:)` walk, and returns `nil` if unsettled. Why: once the position carries less than one ordinal of precision, floor and ceiling no longer bracket the nearest computed beat. At origin `1e15`, 140 BPM, time `-930114126015926.9`, the two-candidate rule returned `-4503599627370497` (distance 0.375) while `-4503599627370496` sits at 0.125; at origin `1e16`, 120 BPM, ordinals `-2...2` all lie at distance 0 from `1e16`, and the lower-ordinal tie rule requires `-2`, not the `0` the two-candidate rule returned. On ordinary grids the walk ends at the same ordinal DD-12 describes (the midpoint and exact-tie rows are unchanged). A neighbour outside the `2^53` ordinal domain, or with no finite time, is never nearer, and the query returns `nil` when the chosen ordinal has no defined time (origin 0 at a tiny 3.003849708984722e-306 BPM, time `.greatestFiniteMagnitude`: position 9.0, `time(ofBeat: 9)` undefined, so `nil` instead of the former `9`). The same out-of-domain rule now lets the `beats(in:)` bound walk settle on `+-2^53` instead of returning `nil`. Other review fixes: `BeatGridAnalysisSpan` also requires a finite `decodedSampleCount / sampleRate`; `BeatGrid.description` appends `span:`; the beats-inside-the-span claim is qualified to analyzer output before any `offset(by:)`; the `Options` docs for `detectDownbeats`, `maxSeconds` and `beatGridCoverage` point at `hasTrustedBarOrigin` and `analysisSpan`. `BeatGridAnalysisSpanTests` and `PlayableBeatGridTests` now hold 35 tests (13 and 22).

## Design Notes

- DD-1 `coverage` keeps meaning the request (`BeatGridCoverage.swift:59-63`); the new field records the realized span. Rejected: redefining `coverage`.
- DD-2 Integer sample bounds plus `sampleRate`; seconds are computed. Only `sampleRate` can be NaN, so one finiteness rule, as for `tempoLockOctaveFactor` (`BeatGrid.swift:216-221`). Rejected: Double seconds (extra sanitization site, rounds the exact window).
- DD-3 The span is the onset-analysis window plus decoded length, nothing else. Observed-beat extent is `beats.first` and `beats.last`. No `wasTruncated` flag: `analyze(decoded:)` has no file length; compare `decodedDurationSeconds` with `PCMBufferReader.fileDuration(url:)`.
- DD-4 Any unreadable or incoherent span folds to nil, never clamped, never thrown from `BeatGrid.init(from:)`. This is deliberately broader than the anchor policy (`BeatGrid.swift:411` throws on malformed structure, then `:305-309` drops an incoherent value): the span is optional provenance, so wrong types and missing nested keys also fold to nil. The field doc states this.
- DD-5 No `schemaVersion` bump: additive optional field; absent means unknown; Hilbert keys its cache on `currentSchemaVersion` and a bump would force a library re-analysis for a field it does not read yet.
- DD-6 `offset(by:)` leaves the span alone: it is a presentation shift, the analyzed audio did not move, and integers take no fractional shift. Every other forwarder carries it (W52).
- DD-7 Two defaulted internal parameters on `estimateBeatGrid`; direct unit-test calls get nil. Rejected: deriving the span from envelope length times hop (depends on STFT framing).
- DD-8 `PlayableBeatGrid` is a separate public type built from primitives so Hilbert can construct it from its stored projection (`2manyDJs/2manyDJs/Hilbert/Models/IndexedFile.swift:31-48`, sibling checkout). `bpm` is not range-clamped, matching `BeatGrid.swift:56-62`. Rejected: methods on `BeatGrid` only; static functions over raw doubles.
- DD-9 Ordinal 0 is the origin; `time(ofBeat: n) = originTime + (60.0 / bpm) * Double(n)` per ordinal, never accumulated. An ordinal is not `beatIndex` and not a bar number. Negative times are returned as computed.
- DD-10 `beats(in:)` returns ordinal bounds whose membership matches `time(ofBeat:)` exactly: compute candidate bounds from positions, then walk each bound by whole ordinals while `range.contains(time(ofBeat:))` disagrees with the bound, at most 8 steps per bound; if still unsettled (a huge origin collapses many ordinals onto one representable time) return nil. Bounded work, no allocation, no cap on range width. Rejected: a one-step correction, which fails when inverse positions collapse (origin 1e16, period 0.5); the demo's `[Double]` with a 100k cap.
- DD-11 Any query whose ordinal position exceeds 2^53 in magnitude, whose input is non-finite, or whose derived value (`60.0 / bpm`, a position, a time) is non-finite returns nil; `init?` additionally rejects a `bpm` whose period is not finite. Integer ordinals are bounds-checked as `Int` before conversion to `Double` (2^53 + 1 rounds), and `abs(Int.min)` is never evaluated (the same 2^53 bound the guide reports for Hilbert's `beatIndex` guard). Doubles past 2^53 do not hold every integer, and `Int(_:)` traps.
- DD-12 `nearestBeat` compares the distances to the two computed candidate times (floor and ceil of the position) and returns the lower ordinal only when those distances are equal, matching `repositioningAnchor`'s distance comparison (`BeatGrid.swift:621`, `:689`, `:698`). Rounding the position would disagree with that rule when the two distances differ by an ulp (origin 0.337, 128 BPM, time 3.852625: position 7.5, beat 8 nearer).
- DD-13 `hasTrustedBarOrigin` is `source == .manual`, or `source == .downbeat` with `downbeats == .detected` (`BeatGrid.swift:254-262`). `beatInBar` takes `beatsPerBar` from the caller; no meter helper, because no BBBK operation changes grid density (refinement bounded under an octave, locks octave-normalized onto the grid). Rejected: a `beatInBar(at:)` that assumes 4/4 for a `.manual` origin.
- DD-14 No fitted timing, no new anchor-source case, no trace field: the 15.7 wiring stays gated on 15.9 (the constraint is recorded in the 15.7 file by this story).
- DD-15 Doc fixes: a tempo lock does not re-anchor `gridOrigin` (`AudioAnalysisService.swift:2039`, `BeatGrid.swift:367-378`); only refinement selects the origin at the new tempo (`BeatGridAnalyzer.swift:419`). README `:296` points at `hasTrustedBarOrigin`.
- Out of scope (recorded so the implementer does not drift): fitted tempo or phase in the public grid and the 12.1 "fitted phase survives downbeat selection" test (15.7, gated on 15.9); comb refit phase (15.9); long controls and drift scoring (15.9, W96); variable tempo (W100); edit commands beyond the existing two (Hilbert editor); echoing options on the result; demo adoption (later demo-UI story under the CLAUDE.md demo rule); anything in Hilbert; `WaveformAnalyzer` streaming or stereo (15.4a, 15.4b); `SignalSource.beatGrid` wiring (W53); Epic 12 levers; flipping `refineBeatGridTempo`; any rekordbox parity statement; a beat-grid DocC topic group (none exists today; auto-curation suffices); the CLAUDE.md Key Types beat-grid gap (already a deferred item).
