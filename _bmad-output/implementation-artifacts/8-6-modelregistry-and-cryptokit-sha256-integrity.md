# Story 8.6: ModelRegistry + ModelRegistryEntry + ModelRegistryError + CryptoKit SHA-256 integrity

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a **library consumer**,
I want **a public `ModelRegistry` that lists bundled (if any) + user-added + known-public-reference models with CryptoKit SHA-256 integrity validation at registration time**,
so that **ML model misuse (corruption, wrong-version weights, silent disk swap) surfaces as a typed `ModelRegistryError.integrityCheckFailed(expected:actual:)` rather than as silently-wrong BPM output.**

## Acceptance Criteria

1. **Three new public source files.** New files `Sources/BoomBoomBoomKit/ModelRegistry.swift`, `ModelRegistryEntry.swift`, `ModelRegistryError.swift` exist; all public types are `Sendable`. `ModelRegistry` exposes `register(url:expectedDigest:metadata:) throws -> ModelRegistryEntry`, `entries: [ModelRegistryEntry]`, and `lookup(identifier:) -> ModelRegistryEntry?`. `ModelRegistryEntry` carries identity (`identifier: String`), integrity (`digest: ModelDigest`), capability (`capabilities: Set<ModelCapability>`), and attribution (`license: String?`, `sourceURL: URL?`). `ModelDigest` is a library-owned 32-byte integrity-fingerprint value type (`Sendable, Hashable, Codable`; `init(bytes:) throws`, `init(hex:) throws`, `bytes`, `hexString`) — co-located in `ModelRegistryEntry.swift` per **DD-2/DD-9**, adopted over CryptoKit's `SHA256.Digest` because that type has no public bytes/hex initializer (a consumer cannot reconstruct a pinned digest from a published manifest or persisted hex — see **DD-9**). `ModelRegistryError` is an enum with at minimum `.integrityCheckFailed(expected: ModelDigest, actual: ModelDigest)`, `.invalidDigest(reason: String)`, `.modelResourceMissing(URL)`, and `.unsupportedFormat(reason: String)`. [Source: epics.md#Story-8.6 AC1; architecture.md#FR-32]

2. **KDD-C5 digest algorithm, zero new deps.** SHA-256 is computed via `SHA256.hash(data:)` (or the byte-identical incremental `SHA256()` + `update(data:)` form — see DD-5) over `.mlmodelc` directory contents **sorted by relative path with concatenated bytes** (KDD-C5 algorithm verbatim). Zero new external dependencies enter `Package.swift`. Computation is hardware-accelerated on Apple Silicon (CryptoKit default). The finalized 32 bytes are wrapped into the library-owned `ModelDigest` at the hashing site (`ModelRegistry.computeDigest`) — the sole CryptoKit touch-point (AC3, DD-9). [Source: epics.md#Story-8.6 AC2; architecture.md#L165-167 "SHA-256 over `.mlmodelc` directory contents (sorted-by-relative-path, concatenated bytes)"]

3. **CryptoKit confined to `ModelRegistry.swift` alone.** Because the public API now carries `ModelDigest` (not `SHA256.Digest`), CryptoKit is touched in exactly ONE place — the internal `computeDigest` helper in `ModelRegistry.swift` that hashes bytes and wraps the result into `ModelDigest`. `ModelRegistryEntry.swift` (incl. `ModelDigest`) and `ModelRegistryError.swift` do NOT import CryptoKit. This satisfies the epic's literal "and only to `ModelRegistry.swift`" — which the adoption of `ModelDigest` makes achievable where `SHA256.Digest` in the public API made it impossible (see **DD-3/DD-9**). Gate: `grep -rn "import CryptoKit" Sources/BoomBoomBoomKit/` returns ONLY `ModelRegistry.swift`. [Source: epics.md#Story-8.6 AC2; architecture.md#L192]

4. **Cache-on-first-load.** Per KDD-C5, when `register(url:expectedDigest:metadata:)` is called twice with the same URL, the second call short-circuits the SHA-256 computation and returns the cached result — verified by a test-only digest-computation counter (`@testable`-visible internal). Cache is in-memory only (no cross-launch persistence — that is the consumer's responsibility, per NFR / FR-32). [Source: epics.md#Story-8.6 AC3; architecture.md#L167 "Computed once per registration; cached"]

5. **Integrity mismatch throws, registry unchanged.** When a fixture model at `Tests/BoomBoomBoomKitTests/Fixtures/Models/tampered.mlmodelc/` is registered with a wrong `expectedDigest`, `register` throws `ModelRegistryError.integrityCheckFailed(expected:actual:)` with both digests populated; the registry's `entries` array remains unchanged (the throw happens before any append); no silent acceptance. [Source: epics.md#Story-8.6 AC4]

6. **`modelIdentifier` cross-link + README section.** A DocC cross-link is added between the producing-model identity field and `ModelRegistryEntry.identifier`, and a README "Model registry" section is added. (The epic's premise — "Story 6.2 left an internal `BPMDiagnosticTrace.modelIdentifier` unannotated" — is **factually wrong**: no such field exists. The actual equivalent, `MLEvaluation.modelIdentifier`, is **already `public`** at `MLTechnique.swift:59`. So this AC reduces to DocC cross-linking the already-public field and adding the README section — see **DD-1**. No internal field is promoted because none exists.) [Source: epics.md#Story-8.6 AC5; Sources/BoomBoomBoomKit/MLTechnique.swift:53-59]

7. **In-memory-only API surface (no persistence methods).** There is no `save(to:)` / `load(from:)` method on `ModelRegistry`. Demos and consumers handle persistence via their own bookmark + `UserDefaults` plumbing (Epic 10's responsibility). [Source: epics.md#Story-8.6 AC6; architecture.md#FR-32 "In-memory only at library level"]

8. **Test suite coverage.** New test suite `Tests/BoomBoomBoomKitTests/ModelRegistryTests.swift` covers: happy-path registration (digest match), failure-path (digest mismatch → typed error, entries unchanged), cache reuse (second `register` short-circuits — counter asserted), and `Sendable` conformance (concurrent `register` from multiple `Task`s does not corrupt the entry array). [Source: epics.md#Story-8.6 AC7]

9. **No regression / BPM byte-identity.** The full unit suite stays green and the default `analyzeBPM` path is byte-identical — `ModelRegistry` is a brand-new, opt-in type wired to nothing in the analysis pipeline (it is a consumer-facing catalog, not a pipeline stage). `make fmt` idempotent; `make lint` clean (only the pre-existing `LUFSAnalyzer.swift:135` baseline violation). [Source: project regression discipline; CLAUDE.md "Design Constraints"]

## Dev Notes

### Why this story is low-risk and self-contained

`ModelRegistry` is a **standalone consumer-facing catalog**. It is NOT wired into the BPM/LUFS/beat-grid pipeline, the ensemble, `Options`, or `AudioAnalysisService`. Nothing in the analysis path reads it. That is why AC9 (BPM byte-identity) holds by construction — there is no pipeline edit. The whole story is: three new source files (`ModelRegistry` + the `ModelRegistryEntry`/`ModelDigest`/`ModelCapability`/`ModelMetadata` value types + `ModelRegistryError`) + one new test suite + a DocC cross-link + a README section. Treat any temptation to "wire it into model selection" as out of scope (that is Epic 10's `ModelPickerView`, which *reads* the registry).

### Decisions / factual corrections to the epic ACs (READ BEFORE CODING)

These came out of a pre-spec grep of the actual codebase. The epic ACs carry three claims that do not match the code; each is resolved here.

- **DD-1 — There is no internal `BPMDiagnosticTrace.modelIdentifier` to "promote."** Epic AC5 says "Story 6.2 left an internal `BPMDiagnosticTrace.modelIdentifier: String?` field (or equivalent) unannotated → promote it to public." Reality (grep): the only `modelIdentifier` in the core target is `MLEvaluation.modelIdentifier: String?`, which is **already `public`** (`Sources/BoomBoomBoomKit/MLTechnique.swift:59`). The other is `BNNSTechnique.modelIdentifier` (internal, in the *ML* target — out of core, out of scope). So AC6 here reduces to a **DocC cross-link** between the already-public `MLEvaluation.modelIdentifier` and the new `ModelRegistryEntry.identifier`, plus the README section. Nothing is "promoted." Do not fabricate a trace field. [memory: feedback_factual_claims_grep_pre_story, feedback_direct_about_failure]
- **DD-2 — `ModelCapability` is a NEW type the AC forgets to name.** The AC's file list names exactly three new files but `ModelRegistryEntry.capabilities: Set<ModelCapability>` requires a `ModelCapability` type that does not exist. Co-locate it (and `ModelMetadata`) in `ModelRegistryEntry.swift` to honor the explicit 3-file enumeration and keep root `.swift` files under the "subdir when ≥ 5 cohesive files" threshold (architecture.md#L149). A dedicated `ModelCapability.swift` would also be defensible (still < 5) — co-location is the recommendation, not a hard rule.
- **DD-3 — `import CryptoKit` IS now confined to one file (via `ModelDigest`); `ModelRegistry` must be a class, not an actor.**
  - *CryptoKit confinement (revised 2026-06-14 — see DD-9):* The original draft kept `SHA256.Digest` in the public API of all three types and concluded confinement to one file was impossible. That conclusion is overturned: adopting the core-owned `ModelDigest` wrapper (DD-9) removes `SHA256.Digest` from the public API entirely, so `ModelRegistryEntry.swift` and `ModelRegistryError.swift` no longer import CryptoKit. CryptoKit is touched in ONE place — `ModelRegistry.computeDigest`, which hashes bytes and wraps them into `ModelDigest`. This makes the epic's literal "only `ModelRegistry.swift`" achievable (AC3). Pre-1.0, breaking the drafted `digest: SHA256.Digest` naming is free.
  - *Class vs actor:* AC1 gives `entries` and `lookup(...)` synchronous signatures and `register(...)` a synchronous (throwing, non-async) return. An `actor` forces `await` on all of these. Therefore `ModelRegistry` is a `public final class: Sendable` with a `Synchronization.Mutex<State>` guarding all mutation. AC8's "concurrent register does not corrupt the entry array" is satisfied by the Mutex, not by actor isolation. Precedent: `AudioAnalysisService.swift:1617` (`Mutex<FeatureSubstrate.DecodedAudio?>`), `BNNSTechnique.swift:140`.
- **DD-4 — `expectedDigest` is optional (TOFU vs pinned).** Make it `expectedDigest: ModelDigest? = nil`. `nil` = trust-on-first-use: compute, record, register (the "user-added model" path — the consumer has no pre-known digest). Non-`nil` = verify-or-throw (the "known-public-reference model" path — the consumer pins a known digest and wants a swap detected). The consumer builds that pinned `ModelDigest` from a published/persisted hex via `ModelDigest(hex:)` — the exact workflow `SHA256.Digest` cannot serve (DD-9). Document plainly that TOFU is **pin-now-detect-later**, not verified provenance. This shape supports both the happy-path test (pass the matching digest) and the mismatch test (pass a wrong one).
- **DD-5 — Digest algorithm: incremental hash over sorted files (byte-identical to "concatenated bytes").** KDD-C5 verbatim is "SHA-256 over `.mlmodelc` directory contents sorted-by-relative-path, concatenated bytes." Implement with `var hasher = SHA256(); for file in sortedFiles { hasher.update(data: Data(contentsOf: file)) }; let digest = try ModelDigest(bytes: Array(hasher.finalize()))`. Feeding the sorted file bytes incrementally produces the **same** digest as hashing one concatenated `Data`, without materializing the 1.26 MB `weights/weight.bin` (and future larger blobs) into a single buffer. *Boundary note for the reviewer:* KDD-C5 concatenates file *contents* only — it does NOT interleave the relative-path bytes into the hash. That means two different directory layouts whose files concatenate to the same byte stream would collide. This is a theoretical cross-layout collision, **not** a tamper-detection gap (any byte change to a registered model still changes the digest). Implement verbatim; if a reviewer wants path-mixing hardening, that is a follow-up, not this story.
- **DD-6 — digest-computation counter + lock discipline.** The cache test needs proof the second `register(sameURL)` does not recompute. Keep an internal `digestComputationCount` bumped exactly once per actual SHA computation. Cache key = standardized URL (`url.standardizedFileURL`). Note: computing the digest does file I/O; holding the `Mutex` across I/O is acceptable here (registration is not a hot path and keeps cache/append atomic), but if you prefer not to hold the lock across I/O, use the double-checked pattern (lock → check cache miss → unlock → compute → lock → re-check/insert/append) and ensure the counter still reflects real computations. Either is fine; document which you chose.
- **DD-7 — `ModelRegistryEntry` is `Sendable, Hashable` but intentionally NOT `Codable` (rationale revised 2026-06-14).** The original reason ("`SHA256.Digest` isn't `Codable`") is void — `ModelDigest` IS `Codable` (DD-9). The entry stays non-`Codable` for a stronger reason: its `url: URL` encodes as a bare path string that does NOT round-trip a security-scoped sandbox file, so a synthesized `Codable` would be a persistence footgun — a consumer would think they could serialize+restore an entry when the URL won't re-resolve under sandbox. Epic 10 persists a security-scoped bookmark + `identifier` + the `ModelDigest` hex and re-registers; `ModelDigest` being independently `Codable` makes that fingerprint trivially storable. Add a DocC note saying the entry is non-`Codable` by design (persist a bookmark, not the URL). Reconsider only if a real consumer needs a bookmark-aware entry codec (pre-1.0; no BC concern). [memory: feedback_no_bc_goal_prerelease]
- **DD-8 — No persistence methods (AC7 / FR-32).** No `save(to:)` / `load(from:)`. Persistence is the consumer's job (Epic 10 security-scoped bookmark + `UserDefaults`, mirroring the Story 5-6 `MergeStrategyPersistence` precedent named in epics.md#L330).
- **DD-9 — `ModelDigest` value type adopted over CryptoKit's `SHA256.Digest` (decided 2026-06-14, party-mode reflection + Codex consult, operator-approved).** CryptoKit's `SHA256.Digest` exposes byte iteration and `description` but **no public initializer from bytes or hex** — it can only be produced by hashing data. So `expectedDigest: SHA256.Digest?` makes the pinned-digest path (DD-4) unusable: a consumer cannot turn a published-manifest hash or a persisted hex string back into a `SHA256.Digest` to verify against. The fix is a thin core-owned `public struct ModelDigest: Sendable, Hashable, Codable` over 32 bytes with `init(bytes:) throws` / `init(hex:) throws` + `hexString`. Three downstream effects, all positive: (a) it replaces `SHA256.Digest` in the entry/error/register API, so CryptoKit confines to `ModelRegistry.computeDigest` alone (DD-3, AC3 — now matching the epic's literal claim); (b) it is independently `Codable`, so consumers persist the fingerprint without the entry being `Codable` (DD-7); (c) it enforces a 32-byte invariant a bare `Data` would not (`.invalidDigest` on bad length/hex). A bare-`Data` alternative was considered and rejected for losing that semantic length guarantee. A pluggable validation callback (`.none`/`.sha256`/`.custom` closure) was also considered and rejected as YAGNI — `nil` vs a `ModelDigest` value already expresses the only two real modes (TOFU + pinned SHA-256); no concrete third validator exists, and pre-1.0 a `.custom` seam can be added for free the day one does. [memory: feedback_no_bc_goal_prerelease, feedback_options_struct_pattern]

### Review Findings (bmad-code-review, 2026-06-14)

Three-layer adversarial review (Codex Blind Hunter [diff-only] + Edge Case Hunter [diff+project] + Acceptance Auditor [diff+spec]). Acceptance Auditor: all 9 ACs + all 9 DDs PASS, objective gates (CryptoKit single-file, zero deps, README discipline, bidirectional cross-link) independently re-verified. The findings below are robustness/integrity-design observations, not AC failures.

**Decision needed (2):**

- [x] [Review][Decision] (RESOLVED 2026-06-14 → Option B, hardened + applied; Codex cross-check thread `019ec8fe` agreed with B on format-stability grounds) Contents-only digest hides structural changes + is non-deterministic under duplicate relative-path keys — `computeDigest` hashes file *contents* only (`ModelRegistry.swift:244-256`), never relative path / length / count. Consequences: (a) adding or removing a **zero-byte file** leaves the digest byte-identical (empirically confirmed by two layers) — this **falsifies DD-5's own claim** that contents-only is "not a tamper-detection gap"; (b) the documented cross-layout collision (DD-5); (c) the `lastPathComponent` fallback (`:224-230`) + `String <` sort (`:244`, canonical-equivalence, not UTF-8 byte order) can make the **same bundle hash differently across runs/filesystems** when relative-path keys collide. DD-5 mandated KDD-C5 verbatim and deferred path-mixing as a follow-up. Options: **(a)** keep KDD-C5 verbatim and correct the doc comment to admit empty-file/boundary invisibility; **(b)** harden `computeDigest` now — mix each file's `relativePath` (UTF-8) + byte length into the hash and sort by UTF-8 bytes — closing the empty-file gap, the cross-layout collision, AND the nondeterminism in one contained change (pre-1.0, no BC cost; only digest values change, no persisted consumers yet). [source: blind+edge]
- [x] [Review][Decision] (RESOLVED 2026-06-14 → pinned bypasses cache, applied) Pinned `expectedDigest` re-verify is a no-op when the URL is already cached — `register` reads `digestCache[key]` before comparing (`ModelRegistry.swift:117-130`), so a second `register(url: X, expectedDigest: D)` on an already-registered URL compares `D` against the **cached** digest and never re-reads disk. For a type whose stated purpose is "make a silent disk swap surface as a typed error," an in-process pinned re-verify silently does nothing. Documented in the `- Important:` block (`:43-48`) and AC4/DD-6 mandate caching — but that motivation was perf, and pinned re-verify is the type's reason to exist. Option: make a **non-nil `expectedDigest` bypass the cache and always recompute** (surgical — TOFU caching unchanged, so the AC4 `digestComputationCount == 1` test stays green). [source: blind]

**Patch (1):**

- [x] [Review][Patch] (APPLIED 2026-06-14) `Data(contentsOf:)` materializes each whole file, contradicting the doc's no-large-buffer claim — `ModelRegistry.swift:246-256` loads each file fully into memory; the doc at `:157-159` says the incremental design avoids materializing large weight blobs. True for the concatenation, but each individual multi-GB weight file is still fully resident → memory spike. Fix: stream each file via `FileHandle` in fixed chunks, `hasher.update(data: chunk)` per chunk (digest is byte-identical — SHA-256 incremental update is chunk-boundary-independent). Composes with whichever Decision-1 outcome is chosen — apply together to avoid editing `computeDigest` twice. [source: blind]

**Deferred (3):**

- [x] [Review][Defer] Symlink handling unspecified across four sub-cases [ModelRegistry.swift:177-256] — deferred, follow-up (dev pre-review F3 already made an explicit "no special-casing" decision; code fails closed): (a) a top-level bundle URL that is a symlink-to-dir → enumerator yields zero → misleading `.unsupportedFormat: "no regular files"` instead of hashing; (b) a subdir replaced by a symlink-to-dir is not descended (`options: []`) → content silently excluded; (c) symlink vs real path → two cache keys (`standardizedFileURL` does not resolve symlinks) → split entries; (d) a symlink-to-file outside the bundle is hashed as its target bytes. [source: blind+edge]
- [x] [Review][Defer] TOCTOU between hashing and model load (and within the multi-file walk) [ModelRegistry.swift:142, 246-256] — deferred, inherent design limitation (partially documented in the `- Important:` block): the registry vouches for bytes at registration time, but `entry.url` can be swapped before CoreML loads, and a file can mutate between the stat loop and the read loop. Not fixable without filesystem locking. [source: blind+edge]
- [x] [Review][Defer] Empty `identifier` is accepted; `lookup("")` returns it [ModelRegistryEntry.swift:134-167] — deferred, minor robustness, no spec requirement (and `MLEvaluation.modelIdentifier` is itself unvalidated/optional); a non-empty guard would need a new error case not worth inventing now. [source: edge]

**Dismissed as noise (9):** Mutex-held-across-I/O (DD-6 explicitly authorizes; negligible for a launch-populated catalog); special-files-skipped (`.mlmodelc` never contains FIFO/socket/device; empty result still throws); case-insensitive-FS vs case-sensitive-sort (the FS cannot present two case-only-different names on a case-insensitive volume); duplicate-identifiers (documented in `lookup` DocC `:77-80`, intended); and Codex's five confirmed non-bugs (`nonisolated(unsafe)` capture is sound, `%02x` hex formatting is correct, non-constant-time equality is irrelevant for local non-secret file integrity, no re-entrancy/deadlock, hex/32-byte bounds correct); plus the spec-prose "13 tests" vs actual 14 (develop-only doc drift, not shippable code).
