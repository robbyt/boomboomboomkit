## Story

**As a** library maintainer,
**I want** `UnifiedSignalPool` (via its `WeightedSignal` payload) to carry the **exact operative `Float` candidate-score** alongside the existing widened `confidence: Double`, populated but **strictly unread**,
**So that** Story 6.4 (the atomic Stage-3 merge-carrier flip, 6.4b) can read the exact `Float` score off the pool — replacing the `BPMResult.candidates` direct read — WITHOUT performing a lossy/ambiguous `Double → Float` reconstruction across the exact commit where byte-equality is swapped for semantic-equality. This story lands that enrichment under the **still-green byte-equality oracle**, so a score-drift bug surfaces while byte-identity can still bisect it.

## Scope clarification (read first)

Story 6.4a is a **byte-inert, strictly-additive prep PR**. It exists because the party-mode panel (Winston/Amelia/Mary/John, 4/4) + the Codex tie-breaker (thread `019e71d7-e077-74e2-9caa-d98c98983fde`) unanimously ruled that Story 6.4's six coupled changes should split into a **byte-inert prep (this story, 6.4a)** + an **atomic flip (6.4b = the existing Story 6.4)**. The split was ratified by the project lead (2026-05-29) over the epic's "atomic-PR non-negotiable" wording, because that rule's *stated intent* — "no week-long red interval between byte-equality going away and semantic-equality arriving" — binds only the **merge-flip + byte→semantic-test-swap pairing**, which stays atomic in 6.4b. 6.4a moves zero bytes and deletes zero tests, so it does not open a red interval.

**The single deliverable:** add an optional `score: Float?` field to `WeightedSignal`, populate it from the DSP candidate's `.score` (the `score: Float` member of `BPMResult.candidates: [(bpm: Double, score: Float)]` — there is NO nested `Candidate` type; it is a tuple array, `BPMAnalyzer.swift:18`) for the DSP `.present(...)` pool entries, and **read it nowhere**. Note the three-source asymmetry: the file-metadata `.present(...)` signal ALSO constructs a `WeightedSignal` (at `MetadataCorroborator.swift:371`) — it gets `score == nil` via the init default; the ML branch constructs NO `WeightedSignal` (its pool entry is `.absent` / `.abstained`, which carry no payload). The 4 `@Tag(.stage1Floor, .stage2Floor)` byte-equality tests and the three `SignalPoolTests` trace-asserting tests stay green.

**What this story does NOT deliver** (each is explicitly OUT-OF-SCOPE — all land in Story 6.4 / 6.4b):

- **No `CandidateMergeStrategy.merge` signature change.** Frozen signature `merge(windowResults: [BPMResult], candidateCount:, strategy:, votingPolicy:, votingThreshold:) -> BPMResult?` is untouched. (Note: the epic AC's claim that merge takes `[BPMResult.Candidate]` is factually wrong — the param is `windowResults: [BPMResult]`; correction carried for the 6.4b spec, DD #9.)
- **No read of the new `score` field by `merge`, `MetadataCorroborator.apply`, or `EnsembleCombiner`.** Strictly dead in 6.4a (DD #3 — the load-bearing discipline).
- **No removal of `MetadataCorroborator.apply(to:input:)`** (6.4b), **no `EnsembleCombiner` removal** (6.4b), **no `git mv` of MetadataCorroborator.swift** (6.4b).

## Key Design Decisions

1. **Story exists per the ratified B-split.** Party-mode 4/4 + Codex confirmed (a) the Float enrichment CAN be a standalone byte-inert PR, and (b) landing it under the green byte oracle is the primary de-risking of the one-way Float-firewall crossing (6-3 DD #2's "Float → Double → Float round-trip during the one stage where `Double.bitPattern` identity is mandatory"). Splitting EnsembleCombiner instead (option C) was rejected — it spends a PR boundary on an orthogonal-but-not-risky axis.

2. **Float-carrier placement: add `public let score: Float?` to `WeightedSignal`.** The operative score is the DSP candidate's `Float` fusion score, which is per-candidate; `WeightedSignal` is the per-signal payload carried in `.present(...)` / `.demoted(...)`, so the score belongs there (`let`, matching the struct's three existing immutable fields — written once at init). **Why an explicit field rather than recovering `Float(signal.confidence)`:** `confidence: Double` is semantically overloaded — for DSP it is `Double(candidate.score)` (an exactly-widened Float, so technically recoverable), but for ML it is a calibrated probability and for file-metadata it is the `fileMetadataStage1TraceOnlyDefault = 1.0` sentinel. Relying on `Float(confidence)` for DSP requires trusting that a DSP `confidence` is always an exactly-widened Float — fragile and re-introduces the ambiguity 6.4b must not depend on. An explicit `score: Float?` makes the operative carrier unambiguous and `nil`-typed for non-DSP. **FLAGGED for Axiom (`axiom-swift`) + apple-docs MCP validation** of the Codable-evolution + Sendable + Float-precision semantics (see DD #5 + Dev Notes).

3. **Strictly-dead-field discipline (LOAD-BEARING — the panel's #1 risk).** The new `score` is **populated** (set from `candidate.score` when building the DSP `.present(...)` entries in `AudioAnalysisService.buildStage2SignalPool`) but **read by nothing** in 6.4a. The byte floor stays green *precisely because* no live path consumes it (the 4 `.stage2Floor` tests bit-compare `AudioAnalysisResult` core fields flowing merge → apply → EnsembleCombiner, none of which reads the pool field). If any read is wired in 6.4a — including a reviewer/Codex "helpfully" consuming it — the byte floor breaks and the entire safety margin evaporates. Swift does NOT warn on a written-but-unread stored property on a public struct (it is part of the API surface), so this compiles and lints clean; the dev agent MUST resist wiring it and the spec MUST state the forward-reference ("consumed by Story 6.4b's merge carrier flip") so the dead field is not "cleaned up." **Strongest structural guarantee (Codex cross-check):** `WeightedSignal` conforms to ONLY `Sendable, Codable` — NOT `Equatable` / `Hashable` / `CustomStringConvertible`, and there is no `extension WeightedSignal:` anywhere in `Sources/` — so there is NO synthesized `==` / `hash(into:)` / custom `description` over all stored properties that the new field could perturb. That eliminates the entire "additive field silently changes a synthesized conformance" regression class; it is a deeper reason for byte-inertness than "the field lives in the trace." (Caveat: `SignalParticipationTraceEntry.description` reflection-interpolates `\(participation)`, which WOULD now include `score` in its default-reflected string — verified no test asserts on that string, so inert.)

4. **Public-API addition is intentional and pre-1.0-authorized.** `WeightedSignal` is already `public`; gaining a `public let score: Float?` is a declared public-API change (per the access-control discipline this is named in AC #1, not discovered in diff). Pre-1.0, no BC concern. The field is added as a **defaulted `score: Float? = nil` parameter on the existing explicit `public init` (REQUIRED path — NOT a second init)**, which keeps every positional 3-arg `WeightedSignal(bpm:confidence:source:)` call site source-compatible WITHOUT editing it. This specifically matters for the file-metadata construction site at `MetadataCorroborator.swift:371` (a 6.4b-frozen file that must NOT be edited) and the `SignalPoolTests` construction sites — they get `score == nil` from the init default, not from an edit. (Verified by the dev/Amelia review: a defaulted param keeps all positional 3-arg sites valid.)

5. **Codable impact.** `WeightedSignal: Codable`. Adding `score: Float?` extends the synthesized `CodingKeys`; an absent key decodes to `nil` (optional-Codable default), and there is no persisted on-disk data pre-1.0, so round-trip evolution is safe. The `SignalPoolTests` Codable round-trip coverage MUST be extended to assert `score` survives encode/decode (including the `nil` non-DSP case and a populated DSP case). NaN handling (Siri / apple-docs validation, confirmed against the repo's Swift 6.3.2 toolchain): `score` is governed by the SAME `nonConformingFloatEncodingStrategy` already proven for `bpm`/`confidence` — `JSONEncoder`'s default is `.throw` on Infinity/NaN, and the existing `SignalPoolTests.codableRoundTripAllParticipationCases` installs symmetric `.convertToString`/`.convertFromString`, which already covers `Float` and `Double` uniformly. **No new strategy is required.** A `nil` `score` encodes as an **absent key** — Swift's synthesized encoder OMITS a nil Optional via `encodeIfPresent` (it does NOT write JSON `null`); on decode the absent key → `nil` via `decodeIfPresent`. This is the optional path, NOT a non-conforming-float string — so the `nil`-non-DSP case exercises optional decoding, not the strategy. (axiom-data empirically confirmed both the absent-key omission and that `NumericTestHelpers.bitEqual` already has a `Float` overload at `NumericTestHelpers.swift:22-24`.)

6. **Byte-inert proof is an explicit AC, not an assertion.** The 4 `.stage2Floor` byte-equality tests + `SignalPoolTests.{dspPerSourceContract, mlAbsentWhenTechniqueNil, metadataAbsentWhenDisabled}` MUST pass unchanged. Add a paired test asserting the new field's population matrix (DSP `.present` → non-nil `score` equal to the source candidate score; ML/file-metadata → `nil`) WHILE `AudioAnalysisResult` bytes are unchanged. This is the regression contract.

7. **Frozen surfaces untouched.** `grep -n "func merge(" CandidateMergeStrategy.swift` returns the identical parameter list; `MetadataCorroborator.apply(to:input:)` signature + body unchanged; `EnsembleCombiner.combine(...)` call site (`AudioAnalysisService.swift:393`) unchanged. All three are 6.4b's concern.

8. **Story 6.4b (the atomic flip) hand-off.** 6.4b reads `WeightedSignal.score` as the operative carrier when it flips `merge` to consume the pool, removes `apply(to:input:)` (re-expressing `corroborationBoost = 1.25` / `skepticismPenalty = 0.85` as pool weight presets / `.demoted`), removes `EnsembleCombiner`, `git mv`s MetadataCorroborator.swift, and atomically swaps the byte-equality tests for `MergeSemanticEqualityTests.swift`. **The architectural wrinkle 6.4b MUST resolve** (surfaced here, not 6.4a's job): `merge` today aggregates ACROSS windows (`windowResults: [BPMResult]`), but `UnifiedSignalPool` is built POST-merge — so the carrier flip is a pipeline restructuring (where/when the pool is built), not a parameter-type swap. Flag prominently in the 6.4b spec. **6.4b read-path ergonomics:** `SignalParticipation` exposes a computed `.confidence` but NO `.score` accessor — 6.4b reaches the carrier via case-destructuring (`.present(let signal)` / `.demoted(let signal, _)` → `signal.score`); consider adding a `SignalParticipation.score` computed accessor in 6.4b. The carrier 6.4a populates is the POST-merge per-candidate `Float` (from `merged.candidates`), which is exactly 6.4b's read site (it replaces the post-merge `BPMResult.candidates` direct read) — confirmed aligned by the party-mode architect review.

9. **Factual corrections inherited for the 6.4b spec** (verified against code, not relevant to 6.4a's surfaces): phantom `MergeByteEqualityTests.swift`; merge param is `[BPMResult]` not `[BPMResult.Candidate]`; `--filter-tag` is fictional (SwiftPM `swift test` has only `--filter` regex — per 6.1 DD #8 / 6.3 DD #5); epic premise "merged to develop" → "present on `rterhaar/epic-6`" (Epic 6 lands into `rterhaar/epic-6`, never `develop`); `apply`-removal must be a NAMED 6.4b AC (architecture intends it; epic omitted it).
