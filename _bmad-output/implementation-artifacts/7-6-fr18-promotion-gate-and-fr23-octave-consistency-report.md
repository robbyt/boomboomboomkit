### Design Decisions

- **DD #1 — `OctaveEquivalencePolicy` is configurable-but-RESERVED (inert) at runtime.** The epic AC3 says "report the runtime `OctaveEquivalencePolicy` used (from Story 6.5 enum)." Reality (`OctaveEquivalencePolicy.swift:13-37`): the 3 cases exist and the knob is accepted in the selection signature, but **6.5b does not branch on it** — octave behavior remains governed by `MetadataPolicy` (octave corroboration) + the `BPMAnalyzer.resolveOctaveAmbiguity` DSP step. **Resolution:** the FR-23 report documents the runtime's *actual* octave handling (MetadataPolicy-governed + the DSP disambiguation), records `OctaveEquivalencePolicy.default == .octaveAwareWithPenalty` as the *declared-but-reserved* policy, and asserts documented-equivalence against the training-loss octave policy on the **policy intent** (both octave-aware), NOT on a (false) claim that the runtime branches on the enum. This keeps the report truthful and survives a future story wiring the enum.

- **DD #2 — `evaluate_fr18.py` must NOT reuse `eval.py` inference.** `eval.py` runs Python torch/coremltools inference on OA300 only. AC2 mandates the *Swift production runtime path* (`BNNSTechnique` → `AudioAnalysisService.analyzeBPM`, `.mlOnly`). **Resolution:** per-track predictions come from the `FR18EvaluationHarnessTests` benchmark producer (env-gated JSON dump, BNNSImpactTests pattern); `evaluate_fr18.py` is a pure orchestrator/aggregator that consumes that JSON. No Python inference path is added.

- **DD #3 — The v2 model does not exist yet ⇒ dev/operator split (mirrors 7.3/7.5).** KDD-B4 signoff is pending → 7.5's training run hasn't produced `giantsteps_v2_seed_*.mlmodel` / per-seed `model_metadata.json` / `marginal-watchlist-stability.json`. **Resolution:** dev ships + smoke-verifies the evaluator harness against `giantsteps_v1.mlmodelc` (negative control → `byow`); the authoritative 3-seed evaluation + KDD-B5 decision is operator-owned and surfaced as pending at close. The evaluator fails closed (named error) when no v2 checkpoint resolves.

- **DD #4 — `FR18EvaluationHarnessTests` is the one main-bound file; it stays BYOW.** It must not hardcode the develop-only `giantsteps_v1.mlmodelc` path (that would leak a develop artifact reference onto main). **Resolution:** it loads via `BNNS_MODEL_URL` (BNNSImpactTests precedent), env-gated; absent the env var + corpus it no-ops/throws cleanly. Smoke-pointing it at `giantsteps_v1.mlmodelc` is done from the develop-only Makefile target, not baked into the test.

- **DD #5 — Gate (b) is `> 55/82` strictly, NOT the 57/82 DSP regression floor.** `architecture.md:481` defines the ML promotion gate as "OA300 Acc1 > 55/82 strictly (ML must beat the pure-DSP single-window ceiling)." The 57/82 in `OA300BenchmarkTests` is the *DSP* regression floor — a different, stricter number for a different purpose. **Resolution:** `evaluate_fr18.py` gate (b) uses strict `> 55`; the report notes the distinction so a reader doesn't conflate them.

- **DD #6 — Story 7.6 evaluates the FULL GiantSteps (≥ 537/661); the n=150 holdout is 7.7-only.** Epic line 875 frames 7.6's GiantSteps as "minus-holdout = 511 tracks," but the holdout (`giantsteps-holdout-v2.json`) is a Story 7.7 artifact, `.gitignore`'d, and "NEVER read by Stories 7.3/7.5/7.6." **Resolution:** 7.6 computes gate (c) on the full 661 with the 537 floor; it must NOT read or partition against the 7.7 holdout (verified by the 7.7 `grep` guard returning zero hits in 7.6 code).

- **DD #7 — ECE/FR-25 calibration uses `MLDiagnosticSnapshot.softmaxMax`, not the full softmax vector.** The runtime surfaces only the max (+ second-max) probability, which matches the architecture's "bin softmax_max into deciles" definition for ECE_half_double and the `softmax_max_p95` anchor. No need to surface the 256-bin vector through the public API.

- **DD #8 — ECE_half_double subset requires the DSP candidate top-3 (verify the source + survival under `.mlOnly`).** The architecture restricts ECE to tracks whose true BPM is half/double of a DSP candidate top-3. **Resolution:** the producer dumps the DSP candidate list + records `candidateSource` (the exact `BPMDiagnosticTrace` field used); `evaluate_fr18.py` computes the subset via `corpus_common.canonical_ratio`. **Two review-surfaced risks:** (a) under `.mlOnly`, `EnsembleDecision` winner-reconciliation may rewrite DSP-derived trace fields — pre-dev #2 confirms the candidate field survives, else the producer runs a second `.dspOnly` pass to capture candidates; (b) the subset can be small on a well-trained model — gate (d) reports `eceHalfDoubleN` and goes `inconclusive` (→ byow) below N<100 with count-adaptive equal-frequency binning (AC8), so a tiny subset cannot silently "pass" on noise. Report `eceOverall` as contextualizer.

- **DD #12 (BLOCKER fix) — every ML promotion metric binds to `decodedBPM`, never `result.bpm`.** Codex + Amelia verified at `combineEnsemble` that with `ensemblePolicy == .mlOnly`, an *abstaining* ML eval returns the **DSP fallback** as `result.bpm` (and `BNNSImpactTests` already encodes this: `ensembleBPM = bnnsResult?.bpm ?? dspBPM`, and its `ml_acc1` counter excludes abstains). If gates read `result.bpm`/`ensembleWinner`, OA300/GiantSteps/tail/watchlist/LAO/FR-23 accuracy can be a DSP number mislabeled as model accuracy → a clean-looking but WRONG promotion decision. **Resolution:** the per-track schema separates `runtimeResultBPM` (= `result.bpm`, debug/trace ONLY) from `fr18ModelBPM` (= `MLDiagnosticSnapshot.decodedBPM`, the ONLY field every gate reads). Abstained tracks (nil snapshot / non-finite `decodedBPM`) count as model-INCORRECT for accuracy gates (denominator = full corpus) and are EXCLUDED from the calibration subset. The Swift assertion checks finite `decodedBPM`, not finite `result.bpm`. This is the single most important correctness fix in the pre-dev review.

- **DD #13 — the Swift-produces / Python-aggregates seam is a `manifest.json` + seed-namespaced-dir contract, not a trusted subprocess.** Winston: shelling `swift test` from Python is fragile (exit codes conflate crash-vs-one-bad-track; a filter typo runs zero tests and exits 0 with an empty out-dir). **Resolution:** the producer writes seed-namespaced dirs `seed_${N}/` each with a `manifest.json` (seed, checkpointSha256, gitSha, expected/actualTrackCount, unresolvedTracks, harnessVersion); `evaluate_fr18.py` ALWAYS consumes a directory, validates counts from the manifest (not the exit code), and refuses duplicate/mixed seeds. The `--runtime-predictions <dir>` pre-dumped path is the **primary operator workflow** (3 corpus passes over `swift test` are slow); the shell-out is a thin front-door over the same dir-consuming code. Keeping it a benchmark TEST (not a develop-only CLI) is deliberate: the main-bound test is what makes the FR-18 "we evaluated main's runtime" claim true (Winston).

- **DD #14 — seed dispersion tripwire (the ≥2-of-3 vote alone can bundle a fragile model).** Mary: reporting min/max/median while gating on a 2/3 vote discards the variance it should gate on — two seeds passing at 56 & 57 with a third at 40 is fragile yet passes 2/3. **Resolution:** wire the already-computed per-gate `max−min` into the decision: spread over a stated bound → gate `unstable` → `byow` regardless of the vote. median-of-3 is a descriptor only.

- **DD #15 — bimodality tests the NAMED 125/175 failure directly.** Mary/John: Sarle's coefficient is moment-based and confounded (heavy tails false-positive; unequal-mass bimodality false-negative) — wrong default for a *named, specific* failure that FR-25 makes a hard blocker. **Resolution:** default = direct anchor-clustering (fraction of `fr18ModelBPM` within ±3 BPM of 125 AND 175, gate on a stated bound); Sarle's BC is a secondary descriptor; `diptest` is the optional formal test. Cheapest test of the exact pathology, can't be fooled by a tail.

- **DD #9 — Bimodality test stays dependency-light by default.** `scipy` is present but has no built-in Hartigan dip; a `diptest` package is not in deps. **Resolution:** default to Sarle's bimodality coefficient (or a 1-vs-2-component Gaussian BIC) computed with numpy/scipy; the operator may add `diptest` to `pyproject.toml` if a formal dip p-value is wanted. The report names which test was used.

- **DD #10 — Develop/main placement.** Develop-only: `evaluate_fr18.py`, `fr-23-octave-consistency.md` (+ generator), `7-6-fr18-rerun-log.md`, `fr-18-evaluation.{json,md}`, Makefile targets. Main-bound: `FR18EvaluationHarnessTests.swift` only (benchmark target, env-gated, BYOW). `git diff --stat Sources/` must be empty (zero production-source change). [CLAUDE.md decision tree]

- **DD #11 — Smoke negative-control: byow either way, but verify which path v1 exercises.** Intended: `giantsteps_v1.mlmodelc` mis-predicts (bimodal 125/175, softmax_max_p95 0.294) → fails gates → exercises the full `byow` path + every report block. **Review caveat (Amelia/Codex):** Story 7.5 bumped `featureSetVersion` via the shared constant, and v1 was trained on the OLD version — so the runtime may abstain at `featureVersionMismatch` *before inference*, making `.mlOnly` fall through to DSP and the smoke HOLLOW (it tests plumbing, not the ML path). **Resolution:** the outcome is `byow` either way (under DD #12, all-abstain = all-model-incorrect → byow), but pre-dev #3 MUST run `make bnns-impact-report` on v1 and the dev MUST record + assert the actual bucket (`mlAbstained` rate / `featureVersionMismatch` count). If v1 abstains-all, the smoke is honestly labeled a "fail-closed/abstain-path control," and the ML-inference path is instead covered by the always-on synthetic assertion (which must use a v2-version-stamped fixture if a version-matched model is needed) + the operator's real v2 run. The `bundle` branch + ≥2-of-3 math are covered by the AC12(ii) Python fixture test regardless.
