---
id: windowVoting
title: Post-Disambiguation Window Vote
---
**What it does.** Votes on each window's _final, disambiguated_ BPM rather than on raw candidates. After every window has run the full pipeline — including octave disambiguation — the strategy clusters those finished per-window answers with a 2 percent tolerance and, if two or more windows agree, returns the consensus tempo. When no cluster reaches two members it falls back to _maxConfidence_ over all windows. Because it votes after disambiguation, it counts settled decisions, not intermediate peaks. Its resolution behavior is further parameterizable through _VotingPolicy_ (simple majority, confidence-weighted, or threshold-gated).

**When to pick it.** Choose it when each window is individually competent at picking a tempo and you want their finished verdicts reconciled, rather than re-litigating raw candidates that predate disambiguation. It is the most semantically meaningful consensus strategy: a window's vote is its actual output, so agreement means the pipeline reached the same conclusion independently more than once. It pairs naturally with longer files that yield several windows and with _VotingPolicy.thresholdGated_ when you want to reject low-confidence consensus.

**Tradeoff.** Voting on post-disambiguation answers means a disambiguation mistake is baked into the vote — if the octave logic pulls two windows to the same wrong tempo, _windowVoting_ confidently ratifies that shared error instead of exposing the raw candidates that might have revealed the fundamental. And with only one window, or with every window disagreeing, it silently degrades to _maxConfidence_ and inherits that strategy's over-confident-outlier failure, so on short or noisy files it offers no consensus benefit at all despite the added machinery.
